# 播放响度均衡方案

日期：2026-11-17。状态：首版基础均衡已接入各端，默认关闭；未构建安装包或发布。正向增益仍属于后续能力验证。

## 当前实现

设置 → 播放与歌词新增“响度均衡”，复用现有开关与主题，大屏位于播放设置条目中。按设备保存，修改时立即生效，不覆盖用户音量、播放位置和暂停状态。

- playurl 请求携带 `voice_balance=1`；共享 Rust 策略以 −18 LUFS／−1.5 dBTP 计算非正增益，不使用 `target_offset`。保留音乐动态，不提升安静素材。
- 可选响应解析失败不影响音源解析。BV＋CID 绑定的原始描述写入本地 `loudness_cache`，最多 2000 条；离线下载及完整缓存播放可复用，没有描述则原样播放。不为补数据增加网络请求。
- 桌面、Android／大屏、iOS、鸿蒙使用同一增益计划。各输出层分别组合用户音量与曲目增益，Android／鸿蒙还组合焦点压低；设置开关按 dB 在 300 ms 内过渡。
- 前台起播与原生后台解析都携带增益；静音候选在音源交接后应用最新开关，设置版本阻止迟到命令回退。切歌、缺少数据、焦点恢复和音质切换均重新应用一次输出计算。
- 缓存是可再生的本地数据，不加入音乐资料或坚果云协议。新增 schema 8 只增加缓存表，不修改用户音乐资料。

验证记录位于忽略目录 `artifacts/loudness-implementation-20261117/`。一组匿名 AAC 对照中，带／不带参数请求的前 64 KiB 完全相同；这是有限样本的字节核对，不代表所有编码的验证。自动化检查包括共享数值样本、无数据回退、跨端输出计算、持久化、迟到计划／开关、静音候选交接、后台队列、焦点恢复与浅深主题界面。iOS 15 原生模块、Android 原生模块和鸿蒙 ArkTS／共享 Rust 均可编译；实际设备的听感与不同输出路由仍需验收。

## 1. 目标与实现选择

减小切换 B 站视频／分 P 时的主观音量差异，保留同一音频内部的强弱变化。采用整段响度归一化：为每个音频确定固定增益，在播放时应用。不会反复跟随瞬时音量拉高拉低，不改变下载文件或云端音频。

首版建议采用全端一致的保守均衡：以 −18 LUFS 为初始目标，主要降低过响内容；在原生正向增益验证通过后，再允许安全范围内提升安静内容。目标值是本产品的初始参数，不是 ITU 强制要求。没有足够峰值余量时，宁可未达到目标，也不强行放大或压缩音乐动态。

普通音量的 0–1 上限不能当作完整数字增益器。不得只修改音量滑块后声称所有平台都能放大安静素材，也不为此直接重写整个播放器。

## 2. 已完成的接口与代码检查

### B 站数据

现有 `/x/player/playurl` 请求增加 `voice_balance=1`，三个匿名样本均返回 `data.volume`。不需要另加请求、登录或下载音频。

| BV | CID | `measured_i` | `measured_tp` | −18 LUFS 下的增益 |
| --- | ---: | ---: | ---: | ---: |
| BV1Wr4218772 | 1472521075 | −12.7 | +0.8 | −5.3 dB |
| BV1Xt4y1m7v3 | 172917353 | −9.1 | +3.8 | −8.9 dB |
| BV1QrSeY2ETh | 26530087823 | −15.5 | +0.001 | −2.5 dB |

同一 BV 的对照请求中，AAC 三档音轨的 ID、codec、bandwidth 和主 URL 的 host/path 相同。完整 URL 的签名查询参数不同。这支持“客户端利用元数据做补偿”的路线，但没有比较音频字节，不能据此证明服务端绝不处理音频。接入前需使用已有缓存或少量媒体片段对照，排除重复补偿，并检查实际解码响度是否符合预测。

其他注意事项：

- 三例不代表所有视频、账号、音质和地区都能返回这些字段，解析必须可选。
- `measured_i`、`measured_tp` 先作为来源提供的整段响度和真峰值描述；服务器测量标准版本、音轨覆盖范围尚无官方承诺，尤其需要核对 Hi-Res 与 AAC 是否采用相同母带。
- `measured_tp` 可以大于 0，实测达到 +3.8 dBTP；不能因此直接判为缺失。
- **不能把 `target_offset` 直接当作 dB 增益。** 第二例目标与输入之差是 −4.9 dB，但 offset 是 −0.5。该字段的单位和用途未确认。
- 不盲目沿用服务端 `target_i`，应用应使用一个明确、跨端一致的目标。

脱敏响应、URL 映射比较和设计模型保存在被 Git 忽略的 `artifacts/loudness-design-20261116/`；不含用户凭据、CDN 地址和签名。设计模型覆盖 11 个边界案例并对上述三例计算通过，尚未验证实际输出音频。

### 当前播放器

- 桌面：`HTMLAudioElement`，没有 Web Audio 增益图。
- Android／大屏：原生 `MediaPlayer` 前台服务。
- iOS：原生 `AVPlayer`，最低 iOS 15。
- 鸿蒙：`media.AVPlayer`，当前兼容 API 20。
- 均只有普通音量控制，没有 LUFS 分析器或独立响度策略。用户音量、焦点压低和换源恢复目前在多处直接设置，需收敛到唯一输出计算入口。
- B 站 `PlayData` 目前只保留 `dash`，其他根字段被忽略。代理转发压缩音频字节，不等于能够读取 PCM 或直接测量 LUFS。

## 3. 统一策略

初始参数：目标 `T = −18 LUFS`，预测真峰值上限 `P = −1.5 dBTP`。正向增益的产品上限暂定 +6 dB；首版基础能力上限为 0 dB，之后按平台原型结果开放。参数需要音乐、人声、长视频与不同编码的对照测试后定稿。

```text
目标增益 = T − measured_i
峰值允许增益 = P − measured_tp
最终增益 = min(目标增益, 峰值允许增益, 产品正增益上限, 平台增益上限)
线性倍率 = 10^(最终增益 / 20)
```

- 没有响度数据：保持原样播放，不等待分析，不额外请求补齐。
- 只有响度、没有可靠峰值：允许衰减，不允许正向增益。
- 非有限数、离谱数据或身份不匹配：本次绕过。0 是合法数值，不能通过真假值判断缺失。
- 已存在的失真／削波不能靠调低音量修复；峰值保护用于避免本应用再增加溢出。
- 峰值描述属于内容还是某个编码变体必须保留区别。对尚未验证适用的变体，不开放正增益，不能将内容级描述伪装成准确的逐编码测量。
- 片头安静、对白、间奏、渐强段落仍保留；不根据这些段落实时重算增益。

新音频在第一个可听采样前应用补偿，避免先响一声再降低。播放中开关使用约 200–400 ms 的 dB 平滑过渡，关闭时回到原始倍率 1。用户音量为 0 时始终静音。

## 4. 共享结构与数据归属

共享 Rust 层新增纯函数策略和类型，先覆盖前台与原生后台两个入口，再接 UI。

```text
已有 playurl 请求 + voice_balance=1
  → 可选 LoudnessDescriptor
  → 共享 LoudnessPolicy / GainPlan
  → 前台 PlaybackPlan + 原生后台 ResolveResult
  → 各端 applyOutputGain()
```

`LoudnessDescriptor` 保存来源、BV/CID、作用范围（内容／音轨变体）、LUFS、峰值及峰值类型、可获得的音源指纹、采集时间和解析版本。`GainPlan` 记录策略版本、设置版本、目标 dB 和可用能力，不把补偿写回用户音量。

输出状态分开保存：用户音量、曲目增益、焦点 duck 因子、候选播放器静音门。所有音量写入收敛到平台唯一入口，避免焦点恢复、播放恢复、切音质时覆盖补偿。

落点：

- `src-tauri/src/infrastructure/providers/bilibili.rs`：请求参数、可选 `volume` 解析、与 DASH 一起缓存，避免补请求。
- `src-tauri/src/domain/`：共享增益决策；平台代码不复制公式。
- `src-tauri/src/interface/commands.rs` 与 `src-tauri/src/native_playback.rs`：同时扩展前台计划和后台自主下一首解析。
- `src/features/player/playerStore.ts`、`sourceSwitch.ts` 与原生桥接契约：应用设置版本及音源身份。
- 三端原生播放器：统一输出入口与候选交接。

缓存使用独立的本地响度仓储，不混入 Track 的用户覆盖信息，也不进入同步 V2。最低身份为 BV＋CID，变体测量再包含 quality／codec／音源指纹；临时 CDN 签名不能作为主键。缓存有条数上限，按访问时间清理，播放时拿到新元数据则更新。只缓存原始描述，调整目标时重新计算，不保存一份过期的最终增益作为真源。

完整缓存、离线下载命中的播放也查询该仓储，不能依赖每次都请求 playurl。旧缓存没有描述时照常播放；不为补响度而把整首重新下载。

## 5. 平台路线

| 平台 | 基础均衡 | 正向增益路线与验证要求 |
| --- | --- | --- |
| macOS／Windows／Linux | 现有 audio 音量乘独立衰减倍率 | 可验证 Web Audio `MediaElementAudioSourceNode → GainNode`；必须处理 CORS、用户激活、休眠与后台恢复，不能以新增 AudioContext 导致起播静音 |
| Android／车机／TV，含 ARMv7 | MediaPlayer 音量统一叠加补偿 | `LoudnessEnhancer` 可附着到音频 session；支持不代表各厂商表现相同，需检测效果器控制权、重建 session 与路由变化，失败回退基础均衡 |
| iOS | AVPlayer 音量统一叠加补偿 | `AVAudioMix`＋`MTAudioProcessingTap` 是待验证路线，需逐项核实当前网络 AAC／FLAC、iOS 15、后台播放及耗电；不能直接让 volume 超过 1 |
| 鸿蒙 | API 20 用 setVolume 衰减 | API 21+ 可探测 AVPlayer.setLoudnessGain；设置正确 audioRendererInfo，Hi-Res／输出路由不支持时降级。API 20 不为此改写解码器＋AudioRenderer |

第一步各端使用相同的非正增益策略。正增益属于下一步能力验证，不能把 Android 效果器压缩、iOS 普通音量和鸿蒙新 API 解释成已经一致的 DSP。某个平台未通过验证，不阻碍其基础均衡。

桌面若加入 Web Audio，所有音频元素在设置 src 前配置正确 crossOrigin，使用现有媒体代理的 CORS；每个元素只创建一次 source node，关闭均衡时旁路／回到 1，不反复销毁绑定。候选音源也必须遵守。

iOS 的音频 Tap 不在实时回调中分配内存、加锁、发网络或写库；参数更新通过安全的轻量状态传入。按 Apple 文档，不能修改一个已经在用的 AudioMix 输入参数对象来碰运气，应在正确的资源生命周期建立处理链。

Android LoudnessEnhancer 会对超出采样范围的放大信号压缩，不等于任意设置增益都保留动态，也不保证真峰值安全；仍先计算峰值约束。鸿蒙静态 gain 同样不等于自带 LUFS 分析或真峰值限幅器。

## 6. 生命周期、设置与交互

会话检查覆盖：账号会话、播放 generation、音源／媒体 revision、设置 revision、当前 player 实例。迟到的描述只能写入其合法缓存，不能改变新歌曲的输出。

- 原生后台下一首携带同一策略和描述，不能依赖 WebView 仍在运行。
- 渐进起播和音质切换的候选始终静音，提交时按最新设置重新计算，不复制旧播放器已经补偿过的实际音量。
- 切歌先清除旧曲补偿；同 BV 的不同 CID 分开计算。
- 视频元素保持静音，使用权威音频通路，避免重复补偿。
- 焦点丢失／恢复、来电、耳机、蓝牙路由切换均重算输出，不重复切歌或记统计。
- 开关不改变播放位置、队列、暂停状态、下载源或音质选择。

设置 → 播放增加“响度均衡”开关，说明只需“减少不同视频之间的音量差异”。复用共享设置组件与 SettingsDisclosure，大屏接入同一状态，支持焦点和触控。首版建议默认关闭，开启后按设备记住；不增加逐曲弹窗、处理进度窗口和 LUFS 参数面板。

开关按设备保存，音量和音频输出能力本来就因设备而异。分析缓存是可再生数据，不参与坚果云同步，不增加同步请求与流量。未来若同步用户偏好，应显式扩展协议，与缓存完全分开。

## 7. 缺失信息与后续分析

首版不自带 FFmpeg，不在媒体代理中实时解码再编码，不主动下载整首来求 LUFS。这些方案会引入流量、耗电、格式兼容、Range／拖动和起播风险。

如果接口覆盖率实测不足，再单独立项：只对已有完整缓存／下载文件低优先级解码，以 ITU-R BS.1770 兼容的测量器计算整段响度与真峰值，记录分析器版本和音源指纹。先验证 AAC／MP4、FLAC 等支持，再决定依赖。仅扫描片头不能伪装成整段测量；播放中不因零碎分析结果反复改变增益。

长视频各章节内部忽大忽小属于动态范围处理问题。后续可考虑独立的“夜间／人声模式”，不与本次整段归一化混用。

## 8. 实施顺序与验收

1. 扩展脱敏样本：音乐、录音棚、现场、有声书、长视频、多 P、AAC 各档、Hi-Res；核实参数不会导致重复处理。匿名与已登录条件分开记录，风控即停止。
2. 做共享字段解析、缓存、纯函数与桥接 fixture；实现全端基础衰减及原生后台队列支持。
3. 接入设置和输出唯一入口，验证切源、焦点恢复、取消操作等竞态。
4. 单独做桌面、Android、iOS、鸿蒙正增益原型。只有实测通过的能力才开放，不直接替换全部底层播放器。
5. 完成设备验收与回归后再决定目标微调及发布，不将本次设计样本的计算结果当作真机验收。

必要测试：

- 数值：0／缺失／NaN／无穷；正真峰值；静音；峰值不足；缺峰值不放大；dB↔倍率；边界与单位，不误用 target_offset。
- 一致性：共享 JSON fixture 在 Rust、Kotlin、Swift、ArkTS／前端中得到相同计划与允许误差。
- 竞态：快速切歌、同 BV 换 CID、切账号、开关后迟到回调、渐进音质升级取消、后台队列推进、暂停中修改设置。
- 音频：对已有合法测试素材测量处理前后的 LUFS／真峰值；数据可信且峰值不约束的样本达到目标约 ±1 LU；峰值约束样本不强求等响，检查无新增过载、可闻爆音和反复抽吸。
- 性能：同一网络与代理条件下交替比较带／不带参数的 playurl 和起播延迟；不能把 VPN／CDN 波动当作算法收益。基础路线不增加音频下载字节，不新增整首解码，不改变正常后台切歌。
- 平台：iOS 15／新系统、Android 8/9 与新系统／32 位车机、蓝牙、鸿蒙 API 20/21+、桌面休眠恢复；效果器不存在或失败必须正常播放。
- UI：浅深主题、手机窄屏、大屏焦点，开关布局复用现有样式。

## 依据

- [ITU-R BS.1770：节目响度与真峰值测量](https://www.itu.int/rec/R-REC-BS.1770/en)。测量标准与产品选择的播放目标不同。
- [Spotify 官方响度归一化说明](https://support.spotify.com/us/artists/article/loudness-normalization/)。成熟实践使用播放时固定补偿；正增益受峰值余量约束，动态压缩是额外处理选择。
- [Android LoudnessEnhancer](https://developer.android.com/reference/android/media/audiofx/LoudnessEnhancer)。音频 session、mB 单位、放大及压缩行为和不支持异常。
- [Apple AVPlayer.volume](https://developer.apple.com/documentation/avfoundation/avplayer/volume) 与 [audioTapProcessor](https://developer.apple.com/documentation/avfoundation/avaudiomixinputparameters/audiotapprocessor)。普通播放器音量与可处理音频数据的 Tap 是不同能力。
- [HarmonyOS AVPlayer](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/arkts-apis-media-avplayer)。API 级别、范围和 Hi-Res 路由限制同时以本机 SDK 声明核对；本次未作该接口的真机调用。
