# 外部歌单匹配：方案与验证

自动导入使用 `externalSongMatch.ts` 的 `rankImportSongCandidates` 和 `playlistImportModel.ts` 的 `chooseImportMatch`，共享 `songIdentity.ts` 的来源／候选识别。原始歌曲、绑定、迁移和同步的当前规范见 [导入条目与换源](PLAYLIST_MATCHING_SYNC.md)，识别规则见 [共用歌曲识别](SONG_RECOGNITION.md)。分数不是“正确概率”。

当前版本直接保存一个匹配结果，手动查找使用正常 B 站分页搜索，不受原歌曲资格过滤。已匹配歌曲在歌单菜单中「更换视频」，缺项集中到「补全未匹配」；未匹配清单通过稳定条目同步。下文原型评分、旧本机档案和候选界面记录属于历史实验，不是当前数据协议。

## 当前候选选择规则

先验证曲名、歌手、版本与真实 CID；翻唱、现场、串烧和明显时长冲突不能由播放量抵消。识别时统一简繁文字，显示文本保留原貌；MV 标题引用动画／电影名不视为第二首歌。

身份合格后比较综合得分：曲名最多 50 分、歌手最多 24 分、连续时长最多 8 分、对数播放量最多 12 分，歌手相符的官方／MV 标记仅加 2 分。播放量是同曲版本的来源偏好，不是歌曲正确性的证据。“百万豪装录音棚”等展示形式不扣分；明确标注录屏轻扣 4 分，不以零评论直接排除视频，也不额外请求评论数据。

每个关键词粗排前五个候选，至少比较前三个不同 BV 的详情；仍无合格结果才继续剩余两个。没有合格热门结果（至少一万播放）时再用曲名简化查询，最多两个关键词，跨查询复用详情。没有足够候选时比较实际返回数量，不等待凑齐。保持两首流水处理、搜索至少间隔 3 秒、详情至少间隔 0.5 秒以及原有限流退避。相比遇到首个可用上传即停止，这会增加少量详情请求，换取来源比较；不遍历全部搜索结果。

回归覆盖夜航星、红莲华、呓语的热门／冷门竞争、热门错误翻唱、简繁标题、动画引用和简化查询召回。这些公开标题与构造用例验证规则，不代表全站匹配准确率。已有绑定和手选结果不自动批量重写。

## 旧版产品流程记录

- 入口统一为图标加文字的「导入」，来源包括 B 站收藏夹、网易云、QQ 音乐和文本列表；B 站保留复制和双向关联两种方式。
- 外部歌单粘贴后点「开始导入」即自动匹配并分批保存，不强制逐首确认。相近的同版本上传直接选用合理默认值；明确的版本、时长或歌手冲突跳过，不影响其他歌曲。
- 可选的「更换 / 查找」在当前页面内展开候选，支持改关键词和试听；选择后直接保存。请求限流自动退避两次，仍失败则保留进度。
- 外部歌单任务可收起页面继续运行、暂停续导或结束导入；结束时保留已经保存的歌曲。通过 IndexedDB 保留当前账号的最近一个任务，不承诺移动系统挂起应用后仍持续执行。
- 最多同时匹配两首，用流水处理覆盖搜索和详情的网络等待；搜索发起仍统一至少间隔 3 秒，详情发起至少间隔 0.5 秒。候选比较采用上面的当前规则。复用当前账号最近 10 分钟的成功搜索结果（最多 100 个查询，空结果仅保留 1 分钟），继续复用视频详情缓存。保存按原歌单顺序提交。
- 限流后停止新增请求并保留进度：先等待至少 2 分钟，再次限流至少等待 5 分钟，最多自动重试两次。持续受限则暂停并保留更长的冷却时间；恢复后的搜索间隔降速到 6–12 秒，单首成功不清零重试预算。冷却截止时间随任务保存，重开应用或点击继续不会立即重发。这些是客户端策略，不代表 B 站公开配额或承诺的解除时间。
- 已导入的本地歌单菜单中提供「重新匹配视频」，直接从已保存歌曲恢复列表；仅展开指定歌曲时重新搜索，不预搜索整张歌单。候选列表不持久化。替换只改变当前歌单条目，不改全局歌曲主键、其他歌单、喜欢或历史记录。
- 原生读取服务使用独立的无 Cookie 客户端，不向网易云或 QQ 发送 B 站凭据。保存时在账号校验后的 SQLite 事务中按 BVID + CID 去重，保留歌单顺序和已有元信息编辑。
- 不调用大模型，不读取模型 API 密钥，也不上传候选和临时匹配结果到自有云。保存后的普通歌单沿用现有云同步。

### 请求调度的模拟验证

`tests/playlist-import-throughput.test.mjs` 用实际导入代码比较单首串行与两首流水处理，两组都保持 3 秒搜索间隔。四首歌、每首一次搜索和一次详情，共 8 次请求：模拟搜索等待 5 秒、详情等待 0.6 秒时，总耗时从 22.4 秒降到 14.6 秒；搜索等待 0.1 秒时，两组均为 9.7 秒。另有测试验证并发不超过两首、先返回的后曲不打乱保存顺序，以及限流、冷却恢复和暂停。

这验证了两首流水处理可以覆盖慢网络等待，不能代表真实 B 站接口耗时或限制解除效果。相比原来的 1.2 秒搜索间隔，3 秒间隔仍会降低理想网络下的批量吞吐量。

## 目标与取舍

优先减少自动导入错误，其次提高自动完成比例，最后才是速度。不能保证通过文本判断两个音轨是否完全相同。原唱、现场、翻唱、伴奏、重混、加减速、重制、不插电、剪辑和明确标注的语言版本需要分别处理；未标注或错误标注的版本仍可能漏判。

### 1. 来源信息与用户确认记录

获取外部歌曲 ID、歌名、歌手数组、时长、来源别名和版本信息。只使用来源实际提供的别名，不凭空生成译名。建议后续保留来源 ID，以便重复导入时复用用户确认过的对应关系。

用户确认记录应绑定“来源平台 + 歌曲 ID + 版本指纹”，指向真实 BVID + CID。原型尚未实现这层存储。接入时仅为仍在歌单等受保留列表里的歌曲保留映射，移除引用后清理；不建设全站映射数据库。

### 2. 有预算的召回与详情补充

先搜索“曲名 + 歌手”，一页候选。零有效候选时才追加一次更简单的搜索。批量任务建议从单并发、至少 1 秒间隔开始，和用户主动搜索共享节流；实际频率应根据失败情况调整，不能承诺永不触发限制。

第一轮使用标题、UP 名称等轻量字段粗排，建议优先解析前三个不同 BV，缓存详情并在同一导入任务复用。不得对全部搜索结果逐一读取分 P。前三个仍无法确认则转人工，不无限追加请求。原型返回 `detailBvids`，具体网络调度尚未接入。

搜索结果未确认是否多 P 时，不把视频整体时长作为单曲时长，也不自动保存。详情确认后：

- 单 P：用 BV 标题、该 P 的 CID 和时长，BV 与 P1 在展示上合并。
- 多 P：每个 P 独立参与匹配，父 BV 标题只补充歌手和版本上下文。父标题里出现一首歌，不代表所有 P 都是这首歌。
- 歌曲主键始终是 BVID + CID，不按 BV 合并不同 P。

每首通常需要一次搜索，再解析少量候选详情；最坏三次详情仍有成本。100 首歌不能承诺秒级导入。限流时保留进度、退避或让用户稍后继续，不自动切换其他搜索通道反复冲击接口。

### 3. 证据排序与自动选择的门槛

| 证据 | 原型分值 / 处理 |
| --- | --- |
| 曲名一致 | 50；来源提供的别名 46；近似拼写 30，近似只供人工选择 |
| 标题中的歌手 | 全部命中 25，部分命中 20；只有 UP 名称相符仅加 4，不能自动确认 |
| 分 P 时长 | 差值不超过 5 秒或 3% 加 20；允许较宽差值用于排序，但不自动选择 |
| 版本 | 没有发现冲突加 5；冲突扣 30 并禁止自动选择，其他分值不能抵消 |
| 播放量 | 只用于同分候选的展示顺序，不增加可信程度 |

自动选择必须同时满足：真实详情与 CID 已确认、全部已知歌手有标题证据、曲名或明确别名命中、时长接近、无版本冲突、总分至少 88、领先第二名至少 10 分。两个字等短曲名还需要更明确的边界，例如书名号。

未获取详情的竞争者不能被当作低分选项制造分差。即使当前第一名已得到 100 分，若另一个候选补齐详情后可能接近，仍需继续解析或交给用户确认。分值和门槛尚未在代表性真实标注数据上校准。

对比参考项目，典型风险是“标题命中 + 歌手命中 + 时长吻合”已经有 9 分，Live 额外扣 1 分仍超过其 6 分自动阈值；本方案把版本冲突作为不可由其他加分抵消的条件。这里只比较该规则实例，没有声称跑过其完整应用或做过大规模准确率对比。

### 4. 复核与保存

界面分为“建议导入 / 待确认 / 未找到”。自动选择的结果同样可试听和替换；待确认项展示候选、标题、版本、时长和 UP。确认后才写入普通本地歌单，复用现有歌单、元信息覆盖与云同步。

歌曲名和歌手来自导入信息；UP 主仍是 B 站来源信息。现有用户编辑优先，不得被新导入覆盖。临时候选只在本机短期保留，云端仅同步已保存歌单及其必要信息。

## 实际歌单对照后的第二版实验

当时的 `rankDurationFirstSongCandidates` 针对第一版时长档位过粗的问题，使用连续时长分（最高 55 分）与一秒死区。当前已改为身份优先、时长软评分与封顶播放量加分；旧名称仅为兼容转导出，不再维护第二套活动算法。

复现实验：先取得获授权的本地元信息材料，再执行 `node scripts/compare-external-song-match.mjs /绝对路径/实验目录`。比较脚本不发网络请求、不写入用户资料库，也不读取 API 密钥。用户歌单原始材料与模型结果留在本机 artifacts 目录，不作为公共测试夹具发布。

第二版在实际九首样本上调整过，尚无独立留出集或音频真值，不能报告真实匹配准确率。大模型仅做语义辅助，其主观 high 等级不能代替音频证据。新增六项实验排序回归测试覆盖连续时长、版本冲突、外放翻录、双语名及未解析竞争者。

### 缺失项、补齐与原始顺序

每张导入歌单保存独立档案，包含来源歌曲、原序号与已选 BVID / CID；候选列表不保存。原生端档案放在当前账号 SQLite 的 `playlist_import_archives`，IndexedDB 保留活动任务。结束或关闭活动任务后，从歌单进入「重新匹配视频」仍能找回缺失项。旧歌单没有档案时，从当前歌曲列表恢复。

补齐条目按前后原始条目定位插入；替换条目保留现有位置。歌单和档案在同一 SQLite 事务中更新，失败一起回滚；过期替换、目标已存在等情况明确拒绝，避免误删条目。用户已经从歌单移除的已保存歌曲不会自动复活。

导入工作档案仅保存在导入设备，不加入云同步；实际保存的歌单与歌曲正常同步。其他设备尚无该档案时，只能复核已保存歌曲。活动导入期间，音乐库自动同步最多每三分钟放行一次；任务结束恢复正常调度，手动同步和听歌统计独立执行。这样不会因每首导入反复上传工作状态。

### 关联的播放与交互优化

- 队列或当前歌曲改变后立即保存本地快照；进度继续节流，并在窗口失焦、页面隐藏时刷新。正常重启恢复队列已有实现，本次未复现「每次都从最近播放开始」，补上立即退出时的丢失窗口。
- UP 主页面和合集下钻期间保留组件、标签、搜索和滚动位置，返回后恢复浏览状态。
- 播放队列与统计按单 P 使用 BV 标题、多 P 使用分 P 标题；来源显示标题与手动元信息分开，不靠清空用户编辑修复标题。
- 增加可自定义「刷新并同步」快捷键，默认 F5；升级时已有 F5 映射优先，避免覆盖。它只在窗口内生效。
- 下一首可预测时提前预热音源及开头 / 末尾缓存块，最多 512 KiB、六秒预算。复用正常缓存，不预下载整首；暂停、随机、单曲循环不预热，切换账号或队列后丢弃过期的选集解析结果。移动系统挂起前端后不能保证每次都发起预热。
- 桌面播放队列左边缘可调宽并记忆；支持键盘方向键、Home / End 和双击复位；点击外部收起，不打断队列菜单和底部播放操作。
- 编辑歌曲信息可实时读取当前 BV 恢复标题、对应分 P 封面。没有独立歌手或专辑信息时清空相应覆盖，不把 UP 名当作歌手；先填回表单，保存后生效。

验证包括公开歌单读取、分页去重与上限、持久档案复核、补齐 / 替换事务、队列立即落盘、账号隔离、快捷键迁移，以及本机模拟媒体服务器。预缓存测试确认最多读取两个块，随后请求歌曲开头不再访问上游；该测试不受 VPN 或公网速度影响。界面检查覆盖浅色、深色、窄窗口及手机尺寸；预览夹具和截图放在忽略的 artifacts 目录。
