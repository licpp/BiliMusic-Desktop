# 外部歌单匹配：方案与验证

最初的纯算法原型现已接入客户端「导入歌单」页面，未修改播放路径。算法位于 `src/services/externalSongMatch.ts`；实际导入默认选择逻辑为 `playlistImportModel.ts` 中的 `chooseImportMatch`，任务和进度保存在 `playlistImport.ts`。下文保留原型对照过程；分数不是“正确概率”。

## 当前产品流程

- 入口统一为图标加文字的「导入」，来源包括 B 站收藏夹、网易云、QQ 音乐和文本列表；B 站保留复制和双向关联两种方式。
- 外部歌单粘贴后点「开始导入」即自动匹配并分批保存，不强制逐首确认。相近的同版本上传直接选用合理默认值；明确的版本、时长或歌手冲突跳过，不影响其他歌曲。
- 可选的「更换 / 查找」在当前页面内展开候选，支持改关键词和试听；选择后直接保存。请求限流自动退避两次，仍失败则保留进度。
- 外部歌单任务可收起页面继续运行、暂停续导或结束导入；结束时保留已经保存的歌曲。通过 IndexedDB 保留当前账号的最近一个任务，不承诺移动系统挂起应用后仍持续执行。
- 最多同时匹配 3 首歌曲，候选详情最多 3 路并发，复用已有的视频详情缓存。搜索发起仍至少间隔 1.2 秒，慢响应不阻塞其他歌曲；限流后停止当前并发批次并统一退避。保存串行执行，按原歌单顺序提交已完成的连续部分，避免响应乱序打乱歌单。
- 已导入的本地歌单菜单中提供「重新匹配视频」，直接从已保存歌曲恢复列表；仅展开指定歌曲时重新搜索，不预搜索整张歌单。候选列表不持久化。替换只改变当前歌单条目，不改全局歌曲主键、其他歌单、喜欢或历史记录。
- 原生读取服务使用独立的无 Cookie 客户端，不向网易云或 QQ 发送 B 站凭据。保存时在账号校验后的 SQLite 事务中按 BVID + CID 去重，保留歌单顺序和已有元信息编辑。
- 不调用大模型，不读取模型 API 密钥，也不上传候选和临时匹配结果到自有云。保存后的普通歌单沿用现有云同步。

## 目标与取舍

优先减少自动导入错误，其次提高自动完成比例，最后才是速度。不能保证通过文本判断两个音轨是否完全相同。原唱、现场、翻唱、伴奏、重混、加减速、重制、不插电、剪辑和明确标注的语言版本需要分别处理；未标注或错误标注的版本仍可能漏判。

### 1. 来源信息与用户确认记录

获取外部歌曲 ID、歌名、歌手数组、时长、来源别名和版本信息。只使用来源实际提供的别名，不凭空生成译名。建议后续保留来源 ID，以便重复导入时复用用户确认过的对应关系。

用户确认记录应绑定“来源平台 + 歌曲 ID + 版本指纹”，指向真实 BVID + CID。原型尚未实现这层存储。接入时仅为仍在歌单等受保留列表里的歌曲保留映射，移除引用后清理；不建设全站映射数据库。

### 2. 有预算的召回与详情补充

先搜索“曲名 + 歌手”，一页候选。零有效候选时才追加一次更简单的搜索。批量任务建议从单并发、至少 1 秒间隔开始，和用户主动搜索共享节流；实际频率应根据失败情况调整，不能承诺永不触发限制。

第一轮使用标题、UP 名称等轻量字段粗排，建议优先解析前三个不同 BV，缓存详情并在同一导入任务复用。不得对全部搜索结果逐一读取分 P。前三个仍无法确认则转人工，不无限追加请求。原型返回 `detailBvids`，具体网络调度尚未接入。

搜索结果未确认是否多 P 时，不把视频整体时长作为单曲时长，也不自动保存。详情确认后：

- 单 P：用 BV 标题、该 P 的 CID 和时长，BV 与 P1 在展示上合并。
- 多 P：每个 P 独立参与匹配，父 BV 标题只补充歌手和版本上下文。父标题里出现一首歌，不代表所有 P 都是这首歌。
- 歌曲主键始终是 BVID + CID，不按 BV 合并不同 P。

每首通常需要一次搜索，再解析少量候选详情；最坏三次详情仍有成本。100 首歌不能承诺秒级导入。限流时保留进度、退避或让用户稍后继续，不自动切换其他搜索通道反复冲击接口。

### 3. 证据排序与自动选择的门槛

| 证据 | 原型分值 / 处理 |
| --- | --- |
| 曲名一致 | 50；来源提供的别名 46；近似拼写 30，近似只供人工选择 |
| 标题中的歌手 | 全部命中 25，部分命中 20；只有 UP 名称相符仅加 4，不能自动确认 |
| 分 P 时长 | 差值不超过 5 秒或 3% 加 20；允许较宽差值用于排序，但不自动选择 |
| 版本 | 没有发现冲突加 5；冲突扣 30 并禁止自动选择，其他分值不能抵消 |
| 播放量 | 只用于同分候选的展示顺序，不增加可信程度 |

自动选择必须同时满足：真实详情与 CID 已确认、全部已知歌手有标题证据、曲名或明确别名命中、时长接近、无版本冲突、总分至少 88、领先第二名至少 10 分。两个字等短曲名还需要更明确的边界，例如书名号。

未获取详情的竞争者不能被当作低分选项制造分差。即使当前第一名已得到 100 分，若另一个候选补齐详情后可能接近，仍需继续解析或交给用户确认。分值和门槛尚未在代表性真实标注数据上校准。

对比参考项目，典型风险是“标题命中 + 歌手命中 + 时长吻合”已经有 9 分，Live 额外扣 1 分仍超过其 6 分自动阈值；本方案把版本冲突作为不可由其他加分抵消的条件。这里只比较该规则实例，没有声称跑过其完整应用或做过大规模准确率对比。

### 4. 复核与保存

界面分为“建议导入 / 待确认 / 未找到”。自动选择的结果同样可试听和替换；待确认项展示候选、标题、版本、时长和 UP。确认后才写入普通本地歌单，复用现有歌单、元信息覆盖与云同步。

歌曲名和歌手来自导入信息；UP 主仍是 B 站来源信息。现有用户编辑优先，不得被新导入覆盖。临时候选只在本机短期保留，云端仅同步已保存歌单及其必要信息。

## 本次验证

执行：`node --test tests/external-song-match.test.mjs`、`npx tsc --noEmit`。

- 32 项构造场景验证：包括原唱、Live、翻唱、伴奏、Remix、重制、语言、加速版、短曲名、英文单词边界、HTML 实体、多歌手、未知时长、未知分 P、父标题污染、同 BV 不同 CID、候选歧义及详情请求上限。
- 2 项真实接口快照验证：同一个 B 站视频与网易云 5 条歌曲记录的交叉检查。四条普通版本记录为建议自动选择；一条明确的 Remastered 2022 记录转人工确认。**这是一个视频样本，并非五首独立歌曲。**
- B 站视频 `BV1GJ411x7h7`：官方 MV，Rick Astley，单 P，CID 137649199，213 秒。网易云同名普通记录为 212 或 214 秒。快照含来源 URL 与采集时间，位于 `tests/fixtures/external-song-match-live.json`，可离线重复验证。
- 匿名访问 B 站首页成功，但搜索接口返回 HTTP 412。未继续搜索或切换通道，因此**没有验证大批量真实搜索的召回率、整体匹配准确率、完整导入成功率或真实耗时**。

后续应在接口恢复后选取独立标注的真实歌单，分别统计“自动选择中的正确率、自动选择覆盖率、前三候选召回率、每首请求数”。用未参与调参的样本复核门槛，不能把当前构造测试通过率当成真实歌曲匹配率。

## 实际歌单对照后的第二版实验

`rankDurationFirstSongCandidates` 现为导入流程的候选排序器。针对第一版时长档位过粗的问题，改用连续时长分（最高 55 分）与一秒死区；保留曲名和版本约束，补充双语主标题，以及标题/简介中的外放翻录降权。第一版保持独立入口，便于对照。

复现实验：先取得获授权的本地元信息材料，再执行 `node scripts/compare-external-song-match.mjs /绝对路径/实验目录`。比较脚本不发网络请求、不写入用户资料库，也不读取 API 密钥。用户歌单原始材料与模型结果留在本机 artifacts 目录，不作为公共测试夹具发布。

第二版在实际九首样本上调整过，尚无独立留出集或音频真值，不能报告真实匹配准确率。大模型仅做语义辅助，其主观 high 等级不能代替音频证据。新增六项实验排序回归测试覆盖连续时长、版本冲突、外放翻录、双语名及未解析竞争者。
