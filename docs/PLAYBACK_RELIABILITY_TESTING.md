# 播放与收藏夹导入修复验证

记录日期：2026-11-14。此轮只修改代码、执行测试，没有构建安装包或发布。

## 行为

- macOS、Windows、Android、iOS、鸿蒙使用同一个播放计划：完整离线文件和完整缓存优先，其余按目标编码与码率决定是否渐进起播。
- FLAC 或目标码率至少 256 kbps、且至少是候选 AAC 两倍时，先播放轻量 AAC；实际进度前进 0.75 秒后才准备目标音源。普通 AAC 直接播放。
- 自动升级先在后台读取最多 64 KiB，要求估算带宽超过目标码率的 1.35 倍。探测超时或不足时继续原音源；手动音质选择不受该保护限制。自动升级使用独立本地入口，避免污染复用的手动播放入口。
- 新音源准备好并对齐当前进度后交接。暂停、切歌、手动切换音质和跳转进度优先；候选失败保留原音源。
- Android、iOS、鸿蒙保留临时系统打断前的播放意图，重复打断不清除意图；手动暂停、停止或更换歌曲会取消恢复。鸿蒙区分暂停、恢复和降低音量提示。
- B 站收藏夹支持多选、逐个处理、请求间隔和有限退避重试。失败逐项显示，仅保留失败项供重试；复制模式复用目标歌单并去重，保留已经成功导入的歌曲。

任意本地音乐导入已按产品决定移除；已下载的 B 站歌曲仍可离线播放。单视频续播阈值及两个端点（关闭／全部续播）独立于渐进起播。

## 解码性能对照

使用生产 `playerStore`、音源交接逻辑和 Rust `MediaProxy`，由 Chromium HTMLAudio 实际解码。AudioContext 在静音输出前检测 PCM 能量，测量首声和播放中断，避免把 HTTP 首包当成已出声。

测试文件来自同一段 24 秒合成音频：48 kHz、双声道、16 bit，分别编码为约 64 kbps AAC、192 kbps AAC 和约 1.3 Mbps FLAC。M4A 的元数据已位于文件头。每次新建音源标识，避免缓存命中；低、高音源共享同一个限速预算。

两种配置：正常网络为 20 ms 请求延迟、8 MiB/s；受限网络为 180 ms 请求延迟、64 KiB/s。预热后交替顺序，各比较重复三次。下表为首声中位数：

| 目标音源 | 网络 | 直接播放 | 渐进策略 | 结果 |
| --- | --- | ---: | ---: | --- |
| FLAC | 正常 | 123.5 ms | 54.8 ms | 缩短约 56%，三次均成功升级 |
| FLAC | 受限 | 3275.7 ms | 715.5 ms | 缩短约 78%，带宽不足时保持 AAC |
| AAC 192 kbps | 正常 | 52.4 ms | 52.5 ms | 无明显首声收益 |
| AAC 192 kbps | 受限 | 714.3 ms | 719.2 ms | 无明显首声收益 |

正常网络 FLAC 对照的传输量中位数为 3,913,715 → 4,182,040 字节，增加约 6.9%（初始 AAC 与带宽探测）。强制渐进 AAC 的正常网络传输量增加约 45%，因此最终策略让普通 AAC 直接播放。最终策略的 AAC 复测中，正常网络两组均传输 597,690 字节，受限网络固定观察窗口内两组均传输 114,688 字节。

额外连续观察受限网络渐进播放 15 秒，检查实际进度持续前进、已经结束和仍在持续的静音间隔；不能仅凭播放器处于 `playing` 判定成功。候选升级因带宽不足失败属于预期，原音源应持续播放。

入口隔离修复后的最终复测：正常网络首声 50.8 ms，自动升级成功；受限网络首声 723.9 ms，15 秒观察结束时实际进度 14.87 秒，未检测到静音中断。

这些数据证明当前受控音源和网络条件下的收益，不能直接替代五端真机、所有真实 CDN、所有编码格式的测量。

## 排除 VPN／规则代理

- 本机环境设有 HTTP、HTTPS 和 SOCKS 代理；未修改用户的代理或 VPN 设置。
- 受控服务只监听 `127.0.0.1`，基准 Rust HTTP 客户端显式使用 `no_proxy()`；另以连接记录核对浏览器和 Rust 的实际本地直连。
- 真实 B 站探测使用独立 Node HTTPS Agent，无 Cookie、无代理转发。只读取公开视频两种 AAC 音源的前 64 KiB，各两次。
- 实际 CDN 远端 IPv6 的路由为 `en0`，未经过 `utun`。两种码率返回 206，首包约 303–344 ms，总读取约 360–451 ms；这个探测验证直连和连接等待情况，并不是完整起播 A/B 测试。
- 本机原始记录位于被忽略的 `artifacts/checks/startup-benchmark/`，包括矩阵结果、最终复测、连接及路由证据；不保存 CDN 签名地址或账号凭据。

## 自动化与平台检查

```sh
npm test
npx tsc --noEmit
cargo test --manifest-path src-tauri/Cargo.toml --lib
npm run ohos:check
swiftc -frontend -parse native/ios-player/ios/Sources/PlayerPlugin.swift native/ios-player/ios/Sources/InterruptionResume.swift
```

- 前端测试覆盖批量导入部分成功后的重试、限流、取消、空数据、账号切换，以及播放候选失败、暂停、切歌和手动音质优先。
- iOS 打断状态机通过实际 Swift 编译执行；完整插件另做语法解析。
- 鸿蒙测试通过实际 `.ets` 代码配合系统播放器替身，覆盖中断提示和候选音源交接。`ohos:check` 检查共享 Rust 代码，不代表完整 ArkTS 编译或设备验收。
- Android 已增加 Kotlin 打断状态机与对应 JUnit 用例；本机缺少 Android SDK／Kotlin 编译环境，未执行该 JUnit 或 Android 原生编译。
- Rust 测试覆盖缓存完整性、自动升级带宽保护、手动入口复用隔离、收藏夹请求限速及原有同步测试。
- 导入界面已检查浅色、深色、390 px 移动端和 720／1100 px 桌面宽度，截图保存在 `artifacts/checks/four-points/`。

最终结果：前端 231 项通过；Rust 186 项通过，20 项需要显式启用的测试默认忽略；TypeScript、Swift 语法解析及鸿蒙共享 Rust 检查通过。解码基准另外显式运行，未将默认忽略项计为通过。
