# 同步与数据库历史兼容审查

日期：2026-11-14。源码基线：`d848e547bb9feff65345119bb0c90f5088c2e46f`，发布版本 0.3.1。

本次审查确认：问题不只在网络传输。部分历史适配导致同步模型、本机落库及数据库升级流程不一致。应将这些问题作为低流量同步改造的前置工作，不能直接把现有 export 换成增量上传。

以下是源码与合成测试结论；未检查用户实际资料库，因此不表示某个用户已经发生数据损坏。源码修复进度见主方案“实施范围与进度”；当前发布安装包仍未包含这些修复。

## 1. 已确认的问题

### 1.1 合并基准没有按实际同步目标隔离

优先级：P0，影响数据正确性。

`sync/storage.rs::init` 定义 `sync_base(provider PRIMARY KEY,json)`；`sync/mod.rs` 第 374、537 行只按 provider 读取和更新基准。连接/断开逻辑未将这个基准绑定到 WebDAV 目录或远端账号。

同一 B站账号从坚果云目录 A 改连空目录 B，若本机歌单与 A 的旧基准一致，三方合并会把 B 的“没有这首歌单”解释为删除。合成测试直接调用现有 `model::merge`：旧基准得到空结果，新目标使用正确的空基准则保留本机歌单。连接预览是只读，但后续确认合并可能应用错误结果。

修复：基准、最后成功时间、缓存、发布确认均按 `target_id + protocol/domain` 保存。target 绑定规范化 endpoint、远端主体、B站 UID、vault 身份；密码轮换不应平白创建新目标。旧基准只有能证明归属时才能回填到对应目标，不能把无法归属的旧基准自动挂到新连接。

### 1.2 歌词删除落库不完整，会在后续导出重新出现

优先级：P0，影响删除传播及重复同步。

`sync/storage.rs` 第 164 行导出仍存在的歌词行；第 347 行只对传入的 lyric 做 upsert；`prune` 仅删除已无歌曲引用的歌词。对于仍被收藏的歌曲，远端删除其 lyric 记录后，本机旧行没有被删除，下一次 export 又带回旧 lyric。

合成测试使用实际 `storage::apply/export`：输入快照 2 条（track、favorite），apply 后再 export 变成 3 条，旧 lyric 复现。这违反“应用一次同步状态后再次导出应稳定”的闭环要求。

修复：明确歌词同步选择与本机歌词正文/缓存的不同所有权。远端删除同步选择必须落实到对应选择状态，保留应保留的本机正文而不重新生成旧同步事实。不能简单清空整个 lyrics 表；B站字幕和本机独有数据不能被误删。

### 1.3 数据库没有有序版本迁移，打开库还会重置版本号

优先级：P0，阻碍后续结构升级。

`infrastructure/database.rs` 第 18、41 行在打开及切账号时重跑 `0001_initial.sql`；该 SQL 第 104 行无条件设置 `PRAGMA user_version=1`。真实初始 SQL 的内存数据库测试证实：先设置版本 7，再执行初始化脚本，版本变回 1。

目前有些新增结构通过其他模块惰性创建，很多情形能正常运行，但不能据此实现可靠 outbox、迁移恢复或未来版本识别。

修复：引入一个共享数据库迁移入口，事务执行有序 migration、校验并记录执行结果；仅成功后推进 schema_version。首次升级通过结构指纹识别历史变体，不只相信目前一直为 1 的 user_version。遇到更高版本不得回写或降级。访客库、账号库及旧库导入都使用同一入口。

### 1.4 UP 主备注存在于数据库，却不在同步模型中

优先级：P1，功能遗漏。

本机 `creator_notes` 保存备注，`repositories/collections.rs` 第 301 行修改它；`storage::export` 的 collection 只有 bvid/folderId，`model::validate` 的 collection 白名单也没有 note。apply 只有孤立备注清理，没有同步恢复。

合成测试在 A 写入备注，export/apply 到 B，B 的 creator_notes 为 0 行。迁移种子若只复用现有 export，同样漏掉备注。

修复：定义独立的用户备注事实，v2 种子从规范业务层读取；混合 v1 期间保留本机备注，不向旧白名单直接塞新字段。各设备后来加入 v2 时必须补充这类 v1 未表达的本机资料，多端备注不同按真实并发保留候选。

### 1.5 新字段缺失与 null 的编码可能造成重复发布

优先级：P1，流量及版本噪声。

`dav.rs::Doc.update` 把被移除字段编码成 null；`Doc.materialize` 除 history.resume 外会把这个 null 再放进物化记录。若本机规范 export 用“字段不存在”，远端物化用“字段为 null”，两者永久不相等，重复 update 可持续增加设备序号。

具体样例：collectionFolder 曾含 `scope:'collections'`，当前 export 对 collections 范围省略 scope。移除后物化成 scope:null，后续 update 仍认为字段有变化。实际 Doc 加三方 merge 的连续测试表现为每隔一次同步 PUT，序号持续增长；不是每次都上传。此问题依赖云端存在该旧字段形状，不能据此声称所有用户都受影响。Rust 校验允许这个 null，云服务白名单校验则拒绝，两个实现还存在合同差异。

修复：按记录/字段建立唯一规范表示，区分缺失、显式清空与删除；在解码边界做兼容归一化，并同时规范基准与比较对象。不能全局把 null 全删掉，因为 overrideTitle:null 等可能表示合法清空。v2 采用明确操作语义；v1 修复需维持旧读者行为。

### 1.6 文件夹升级逻辑藏在读取与导出路径

优先级：P1，迁移与 outbox 一致性。

`repositories/collections.rs::init_folders` 检查列后 ALTER scope，`separate_legacy_folders` 会拆分混合 UP/收藏文件夹。list、sync export、sync apply 均可能调用它。转换的 UUID 是确定性的，已有幂等测试，没有证据表明它每次创建新的重复文件夹。

问题是“读取列表/查询状态”可能更改业务关系；未来若只在用户写事务里生成 outbox，这些修改会漏记，或者被误记为用户新编辑。

修复：旧库结构/数据迁移移到事务性 migration；旧远端输入的兼容转换放到 importer 边界。业务查询和 export 变成纯读取。设备升级时携带的旧格式材料依然经过 importer，不能以“一次数据库迁移已做过”为由取消输入兼容。

### 1.7 冷恢复缺少稳定的“最近新增”排序事实

优先级：P1，恢复一致性。

当前 playlist、favorite、collectionFolder 与 linkedFolder 的同步没有完整创建/加入顺序。新设备 apply 歌单、关联清单时生成本机当前时间，文件夹还使用 rowid 排序。保留原设备已有顺序的测试不能证明全新设备恢复后相同。

修复：v2 明确同步稳定的 created/add order，接收时间只用于本机诊断，不成为新语义编辑。历史顺序优先从原设备加入时保存的状态取证；多设备不一致或确实没有证据时按确定规则补齐，不能假装能还原从未上传过的真实顺序。成员位置与列表创建顺序分开定义。

### 1.8 约束和废弃字段需治理，但不是发现重复数据的证据

优先级：P2，数据库完整性。

collections.folder_id、creator_notes.bvid 等未用数据库外键表达实际关系，主要依赖应用检查和同步清理。初始 schema 的默认 folder_id='' 也不适合直接加外键。内存 SQL 接受不存在的 folder_id 和孤立备注，只证明约束薄弱，不证明用户库已有孤立数据。

`play_history.progress_seconds` 已无业务读写引用，实际断点使用 playback_positions 与 collection_progress。不能未经统计旧库非零值就删除历史字段。

修复：先审计、修复并备份已有关系，默认引用规范成正式默认实体或 NULL，再加 FK/CHECK/唯一约束；旧断点可证明迁移后废弃旧字段。所有表重建保留歌曲 ID、歌单 ID、成员及因果身份，不以生成新 UUID 代替修复。

### 1.9 历史因果身份被当作当前设备数量

优先级：P1，重装及长期使用后的可连接性。

`dav.rs::Doc.join` 保留已见过的因果 clock，`Doc.update` 第 325 行却按 clock 中的身份数限制最多 10 台。删除旧设备云端文件不会自动去掉其他副本已合并的旧 clock。实际 Doc 测试仅保留一个合并后的文件，累积 10 个历史身份后，第 11 个仍报“最多连接10台设备，请先清理已停用设备文件”。该提示提供的清理方法不能解决这个状态。

修复：分开维护当前安装/发布者清单与历史因果身份。v2 种子保留 legacy 因果命名空间，不能为了设备配额直接删除 clock，否则可能复活删除。历史来源已完整纳入种子也不等于对应安装仍可写入；自动迁移不能要求每一个历史 clock 身份都重新上线 ACK。首台新版完整校验已发布云端来源即可建立 v2，无需等待未知或离线安装；未知本机修改在设备后来加入时重基。休眠与退役仅用于管理，不作为迁移门槛。

### 1.10 次要云协议存在不封闭的降级投影和重复能力探测（本次不实施）

优先级：P1（投影正确性）/P2（请求数）；BiliMusic 云当前禁用，不是现用坚果云的直接故障原因。

`cloud-sync/app.mjs` 给旧客户端隐藏 UP 成员，却保留其文件夹。旧客户端删除这个看似空的文件夹后，服务端兼容保留逻辑恢复隐藏成员，没有恢复其引用的文件夹，校验最终返回 400。已直接调用真实 handler、内存 store 复现。兼容投影必须保持引用闭合，隐藏不支持的数据时要一并处理依赖，不能仅按 kind 过滤。

`sync/transport.rs` 对缺失格式响应头的旧云服务每轮会依次 GET 四次，没有保存协商结果。后续若恢复云服务，应按目标与服务版本缓存能力，失败或版本变化再重新协商。

另有旧 track 字段读取分支在当前严格白名单之后不可达，属于待整理的死兼容代码，不是已证明的重复上传原因。应集中到明确版本的 importer，并与主协议共用合法/非法样例。

## 2. 不应误删的结构

- `system:favorites` 是 favorites 的虚拟歌单投影，不是已证明存在的两套喜欢列表。
- `bili-folder:<id>` 是关联 B站收藏夹的界面身份，关联记录与可刷新的 videos_json 缓存分开是合理设计。
- `linked-folders-v1` 独立同步区是为了旧读者兼容；可以在 v2 统一进入 library 域，混合期不能提前删掉旧区。
- 旧格式导入器、墓碑、来源 ID 和迁移去重映射不是无用历史字段。清除它们可能导致重复累计或删除复活。
- 旧统计原表和累计缓存的重建能力需审查，但本次未证实正常 0.3.0→0.3.1 升级必然导致统计重复，不将其当作已复现故障。

## 3. 目标结构与修复顺序

### 第一层：规范业务状态

本机只保存一个当前规范业务模型。用户事实、平台可刷新缓存、本机专属内容、同步元数据分开；UI 使用规范查询，不需要理解某个旧协议缺什么字段。

歌曲/歌单的稳定 ID 延续现有身份，不因新增 kind 或改字段名重建。当前 `collections.bvid` 同时容纳 BV、season:、up:；可以在领域接口明确为 typed reference，数据库重命名/拆列按收益单独安排，不为了命名整洁一次性重建所有表。

### 第二层：同步语义与事务

业务事务更新规范状态与 outbox；远端输入事务应用已规范化事实，不触发回声。缺失、清空、删除、未同步/本机保留四种情况必须可区分。

建立闭环合同：对每一种同步记录及合法删除，`normalize(export(apply(S))) == normalize(S)`；不属于同步范围的本机资料另外验证保持。相同输入重复应用不新增语义操作、不改变排序、不递增发布版本。

### 第三层：协议兼容适配

v1 importer/exporter 与 v2 codec 都映射到同一规范模型，兼容分支不散落在仓储查询中。旧端不支持某字段，意味着“该协议没有表达能力”，不是要求清空新版字段。能力协商按目标缓存，不能每次层层重拉整库猜版本。

### 交付顺序

1. 建立有序数据库迁移、目标隔离和备份校验；补齐歌词删除、缺失/null 的闭环缺陷。这些不必等 v2，也不能拖到性能优化之后。
2. v1 缓存及独立脏区优化，验证新旧客户端双向合并不变。
3. 明确备注、顺序、引用、断点及本机内容的规范事实与 outbox。
4. 完善即时迁移：首台完整采集已发布云端因果状态后建立 v2；后来设备加入并补充旧 export 无法表达的本机事实、重基未上传修改，不等待所有设备登录。业务覆盖和落库闭环必须通过。
5. 旧库全部转换成功后，停止在正常读写路径使用旧结构。保留只读备份与兼容 importer；历史字段/表按可证明无损的版本化清理策略逐步退休。

本机数据库升级不等于云端协议升级。每台新版可独立升级自己的 SQLite；首台完整校验已发布云端来源后建立 v2，后来新版加入并重基本机修改，不等待其他设备更新。旧版继续使用独立的 v1 目录，新版加入后不再读取该目录；混用期间允许数据暂时不同，各设备升级后处理真实冲突并最终收敛。

## 4. 实施验收矩阵

| 场景 | 必须证明 |
| --- | --- |
| 同服务商换目录/换远端主体/重新连接 | 不沿用错误目标基准，不误删本机资料；相同目标密码轮换保留正确基准 |
| 删除歌词、清空覆盖、字段缺失/null | apply/export 稳定；删除不会反向生成新事实 |
| 不同历史 schema 直接升级、新建库、迁移中崩溃 | 相同规范结构；版本不回退；迁移可恢复且不会重复执行成功步骤 |
| 冷第二设备恢复 | 备注与新模型支持的排序恢复；原有本机正文/缓存不被误清理 |
| 多端收到相同迁移结果 | 迁移事实去重；收包不生成新操作；不重复发布 |
| 旧端回传旧结构 | 在 importer 归一化，不能让本机 schema 退化 |
| 多次重装、清理旧设备文件 | 当前发布者与历史 clock 分离；不靠删除因果信息绕过数量限制 |
| 老协议隐藏部分记录 | 降级投影保持引用闭合，往返不丢隐藏资料、不产生孤立引用 |
| 五端构建、账号切换、访客导入 | 相同迁移入口与领域合同；平台仅适配传输和凭据 |

## 5. 本次证据

忽略目录 `artifacts/checks/sync-compat-audit/` 中的独立 Cargo runner，直接导入当前实际 `model.rs`、`storage.rs`、`collections.rs`，使用内存 SQLite。`cargo run --offline` 已复现：

1. lyric 删除后 apply/export 从 2 条变成 3 条；
2. 错误目标旧基准把未修改本机歌单合并为空，正确新目标空基准保留歌单；
3. 备注导出到第二个库后缺失；
4. 初始化 SQL 把 user_version 从 7 改回 1。

输出保存为 `artifacts/checks/sync-compat-audit/results.txt`。这些是对现状缺陷的观察断言，不是修复后的回归通过证明。修复实现时应将对应用例纳入正式测试并反转期望为正确行为。

另一个 runner 提取当前 `dav.rs::Doc` 实现并调用实际 `model::merge`，验证缺失/null 往返与历史身份上限；输出见同目录 `protocol-results.txt`。云投影测试直接使用实际 `cloud-sync/app.mjs::createHandler` 和内存 store，输出见 `cloud-results.txt`。全部测试只使用合成数据、离线代码和内存数据库，没有接入真实云盘。
