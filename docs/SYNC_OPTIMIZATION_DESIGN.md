# 五端低流量同步设计

设计日期：2026-11-14。核对源码：`d848e547bb9feff65345119bb0c90f5088c2e46f`，客户端基线 0.3.1。

本文是设计与实施跟踪，不代表现有安装包已具备这些能力。适用 macOS、Windows、Android、iOS、HarmonyOS NEXT；五端共用 Rust 协议与 SQLite，实现差异只留在网络、凭据和生命周期适配层。

## 实施范围与进度（2026-11-14）

坚果云的生产同步入口已切换到共享 Rust v2 执行器（`sync/engine.rs`、`statistics_v2.rs`），适用于 macOS、Windows、Android、iOS、HarmonyOS NEXT。BiliMusic 云不参与此次历史兼容与迁移。本地源码已启用，尚未构建、发布新安装包；官网升级提示已准备，尚未部署。

已完成：

- 目标隔离的基准、缓存、成功状态与迁移回执；事务化 schema 迁移、历史文件夹转换和未来版本保护；歌词删除归档、缺失/null 规范化。
- 首台设备一次性读取、验证已发布 v1 主库及关联清单，保留原始因果材料建立 v2。其余设备直接加入，按 bootstrap 原始快照、旧目标基准和本机资料保守合并；即使本机与最后 v1 基准相同，未纳入 v2 的差异仍需处理。正常迁移无额外确认或设备等待；真正的内容冲突需要选择。
- 每个目标持久记录 joined、显示过的字段上下文、备份、确认水位、待发批次和冻结发布计划；已建立本机迁移回执后不退回 v1。上传失败重放相同 generation 和字节。
- 资料库、可选进度、听歌统计分域。同步前从持久 SQL 资料提取语义变化，并在同一事务保存 outbox 和已捕获视图；联网后再次捕获期间修改，再事务应用远端。业务写入无需等待网络，也不会因漏接某个仓储写入钩子而遗漏最终状态。远端应用不制造原创编辑。
- UP 主备注（含清空）、文件夹与列表顺序、关联收藏夹清单参与共享投影。关闭可选播放记录同步不等于删除云端记录。
- 同字段多值、删除与编辑、父记录删除与成员新增冲突保留候选；支持逐项选择三个以上候选。选择绑定本机/远端输入摘要，输入变化后重新展示。恢复成员必须补齐父记录。
- 外部安装身份、序号与提交代水位；发现数据库复制、恢复或不确定预留时更换 actor，保留待发意图及其原观察上下文。统计在记录新样本前检查身份，恢复后更换自身贡献来源。
- 统计采用原 source 的累计单元取最大值，不同 source 才相加。旧缓存重复导入不重复累计；每天与月份总量长期保留，细分明细查询保留 90 天。新版统计加入后不持续读取 statistics-v1。
- gzip、SHA-256 不可变对象、manifest、checkpoint 与不可变 head；只发现最大提交代，缺口/分叉/损坏不应用。持久内容缓存每目标上限 128 MiB，超过后清到 96 MiB；缓存可随时丢弃。目录创建结果持久缓存，409 时恢复目录。
- 每 16 代清理自己过期的 head marker，至少保留最近 8 代。首版保留不可变数据对象、manifest 和因果墓碑，保障长期离线恢复；尚不对这些事实做破坏性 GC。
- Rust 统一单飞、防抖、最大等待、空闲退避、错误退避、持久 Retry-After 与阻塞。资料库冲突/暂停不阻止账号统计。逐请求计量包括失败尝试和鸿蒙上传，统计页显示近 30 天正文流量估计；不冒充坚果云账单。

以下章节保留算法依据、约束和优化路线。二进制编码、全账号可分配硬流量预算、逐请求 token bucket、检查点恢复启发式和数据对象 GC 属于后续优化，未作为当前 v2 已实现能力。当前通过本机合成 WebDAV、故障与多端回归验证；形式化证明、真实坚果云五端实机验收和长期流量测量不能由代码测试替代。

本轮扩展测试与可复现入口见 [v2 同步正确性测试](SYNC_V2_TESTING.md)。接收器按真实因果依赖交错应用不同 writer 的尾日志；提交前在事务中重新核对本机视图；相同的未见候选不能抑制本机真实修改。最近 200 首是显示上限，其缺席不形成全局删除；失去本机最后引用的歌曲事实保留为隐藏恢复材料，避免破坏另一设备或进度域的并发引用。

## 1. 结论与优化目标

采用**持久缓存与条件读取 → 分域增量状态 → 单写者不可变批次与压缩检查点**的路线。保留现有因果合并语义，减少重复传输，不把同步改成按时间戳整库覆盖。

前置审查已确认目标基准串用、歌词删除复活、缺失/null 重复发布、数据库版本回退及备注/排序缺失等问题，详见[同步与数据库历史兼容审查](SYNC_COMPATIBILITY_AUDIT.md)。先完成 A0 正确性治理，再以修复后的 v1 为性能基线；不能直接把旧 export 换成增量上传。

最终目标是：用户修改立即落到本机，云端只传必要变化；没有变化时只探测小型控制信息；播放进度不会带动整个歌单上传；离线、重试、崩溃和多端并发仍能收敛。

优化顺序：正确性 > 用户操作响应 > 传输字节与请求数 > 电量/CPU/存储 > 编码的最后一点体积。纯 WebDAV 没有推送和可靠全局锁，不能同时承诺零轮询流量、秒级跨端可见、任意后台常驻和无限旧客户端兼容。以下参数是初始工程值，须通过第 15 节实验调整。

不改用 SQLite 文件上传，不新增 BiliMusic 中转服务，不要求两台设备同时在线。

## 3. 算法依据与技术取舍

| 参考 | 吸收的机制 | 在本软件中的取舍 |
| --- | --- | --- |
| [Dotted Version Vectors](https://arxiv.org/abs/1011.5808) | 用写入事件与因果上下文区分后继、并发 | 延续当前 dot/context；不用设备时间决定资料覆盖 |
| [Delta State CRDTs](https://arxiv.org/abs/1603.01529) | 可合并的小状态变化，支持重发与重复接收 | 发送带因果信息的字段/集合变化；不能只发送普通 JSON patch |
| [Efficient Synchronization of State-based CRDTs](https://arxiv.org/abs/1803.02750) | 识别重复传播与多余增量，按已知状态减少传输 | 只发布本机产生的变化；接收远端不生成新 outbox；按精确前缀补缺 |
| [CRDT approaches，2024](https://arxiv.org/abs/2310.18220) | 对比操作、状态、增量及其交付条件 | 以状态可合并性配合有界日志恢复，不假设恰好一次网络交付 |
| [Yjs Document Updates](https://docs.yjs.dev/api/document-updates) | 状态向量、缺失更新、重复合并 | 借鉴精确缺失前缀和 origin 标记，不把业务数据库迁入前端 Y.Doc |
| [Automerge 协议](https://automerge.org/automerge/automerge/sync/index.html)及[存储格式](https://automerge.org/automerge-binary-format-spec/) | 持久同步状态、批量压缩、actor 字典与重复值编码 | 学习编码与反熵设计；它的交互协议要求可靠有序双向流，WebDAV 不会运行对等端算法 |
| [Merkle-CRDTs](https://arxiv.org/abs/2004.00107) | 内容寻址、按哈希验证不可变对象 | 批次/检查点用内容哈希；暂不为几台设备建立多层全局 Merkle 树 |
| [rsync](https://rsync.samba.org/tech_report/tech_report.html)、[FastCDC](https://www.usenix.org/conference/atc16/technical-sessions/presentation/xia) | 字节差分、内容分块去重 | 小型结构化记录优先语义增量；纯 WebDAV 没有 rsync 对端，CDC 还增加对象与往返，不作为默认 |
| [HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html) | ETag、条件 GET、304、Retry-After | 实测能力后启用缓存；读缓存失效时恢复完整读取 |

当前活跃设备规模约 1～10 台，精确版本向量很小。Bloom filter/IBLT 的误判修复与交互成本没有明显优势，不用于判断“某次删除已经同步”或决定回收日志。高维树结构、P2P、在线学习调度暂不进入主链路。

本文协议是针对 BiliMusic 与被动 WebDAV 存储的工程综合设计，不声称等同某篇论文的现成实现或已证明达到理论最优。

## 4. 渐进升级：首台建立 v2，其余设备直接加入

**迁移取决于已发布数据的完整性，不等待所有设备登录、更新或超时。** 第一台支持 v2 的设备完整读取并校验云端 v1 后即可初始化；其他新版发现已确认 v2 数据时直接加入，不重新建库，也不要求用户确认。

| 情况 | 新版行为 | 旧版行为 |
| --- | --- | --- |
| 云端尚无 v2 | 采集已发布 v1 来源，校验后建立初始检查点 | 继续使用 v1 |
| 云端已有合法 v2 | 验证身份与提交，加入同一库，合并本机真实待同步修改 | 仍只认识 v1，收不到 v2 新修改 |
| 两台设备同时首次升级 | 使用同一确定性 genesis，各自发布独立 actor 提交，因果合并 | 不影响初始化 |
| 初始化或上传中断 | 重放落盘的同一发布计划，不分配重复操作 | 原 v1 数据保持 |
| 旧设备后来升级 | 先加入 v2，再根据旧基准与 legacy 身份重基未纳入修改 | 只在本机升级时携带原有资料加入 |

### 4.1 可证明的云端覆盖

完整采集主库、关联清单及其 v1 因果状态，记录来源文件与内容摘要；统计继续使用独立来源协议。目录读取失败、来源缺失或校验不通过不能当作空库。保留原始已验证材料及墓碑、候选、引用关系，不只迁移可见歌单。

这证明覆盖本轮观测到的云端数据，不证明获取了其他设备尚未上传的本机修改。采集结束后不再监控 v1；旧请求晚完成或旧端之后产生的资料，由对应设备升级时携带本机数据补入，不要求全局冻结旧客户端。来源集合与逐项摘要形成可恢复的迁移账本；不能用“最后同步时间”代替数据覆盖。

### 4.2 无选主的并发初始化

`Genesis` 由协议常量、B站账号 UID 和规范物理 WebDAV 目录确定。同一目标得到同一 vault 与 seed 身份；登录名别名不分裂远端库，本机缓存仍额外按认证主体隔离。seed 是协议命名空间摘要，具体数据完整性由不可变对象/manifest/head 的摘要验证。

初始化步骤：

1. 读取并验证本轮 v1 来源，持久保存材料与摘要。
2. 将原 dots/context 映射到 `legacy:` 命名空间，按域生成检查点；保留删除和真实冲突。不把 v1 clock 冒充 v2 连续 frontier。
3. 为新安装分配受外部水位保护的 actor，落盘不可变发布计划。没有本机编辑也允许发布初始化检查点，self seq 为 0。
4. 上传对象与 manifest，最后发布 actor 的不可变 head 并读回验证。新编辑进入独立 outbox，不被初始化确认消费。
5. 数据提交确认后才发布固定的 `bootstrap/genesis.json` 标记。发现标记仍须验证可达数据提交；标记本身不代表迁移数据完整。
6. 接收其他初始化 actor 的检查点并合并。相同旧事实保留同一操作身份，不会重复累计或变成新编辑。

每个 actor 只维护自身提交，因此两台首发设备无需共享可变锁或全设备投票。崩溃后按已落盘计划重试；损坏或范围不符的提交保留本机状态并报告错误。

### 4.3 分轨同步与设备一次性加入

决定：迁移完成后，新版只读写 v2，不再扫描、条件读取、导入 v1 云端变化，也不向 v1 回写快照。旧版继续使用原目录；混用期间数据暂时不同。首次 bootstrap 的完整 v1 云端读取是一次性迁移，不是持续兼容读取。已加入设备启动或同步失败时均不得退回 v1。

每台旧设备更新时，先冻结并备份本机输入，再连接同一 v2，完成一次性合并。之后只通过 v2 同步。冻结材料包括当前业务资料、该目标的旧同步基准、可用的本机 v1 因果材料、v1 未表达的备注和顺序、统计自身来源及迁移水位；不得为加入而读取旧云目录。合并前先保留材料，重试不能覆盖这份证据。

**不能仅比较本机资料与最后一次 v1 同步基准。** 设备可能在首台迁移之后已经把自己的修改同步成功到 v1：本机与旧基准完全相同，但 v2 尚未包含这些修改。升级输入必须识别“v2 是否已经包含”，不能以“v1 已同步”当成无修改。

首台迁移按原 legacy dot/context 转换，保留稳定身份。后来设备当前采用原始 bootstrap 快照与目标旧基准的保守合并；将来可利用完整本机因果归档进一步减少不必要的冲突。最后一次旧同步基准仅用于识别尚未上传的额外编辑，不能排除已成功上传 v1 但尚未进入 v2 的资料。普通编辑不隐式恢复存在性；删除/修改并发要显示冲突并保留恢复内容。

旧版没有保存足够因果证据时，结合不可变 bootstrap 材料和目标旧基准判断。只有能证明已经纳入或未变的字段才自动略过；无法证明先后的差异保留为冲突，不擅自以本机、云端或时间戳覆盖。缺失基准不等于空基准，不据此推断删除；缺失字段与显式清空分开处理。不同实体的独有资料可合并，同一实体同一字段不同值保留候选；一边删除、一边修改也需可恢复、可选择。

旧协议遗漏的备注、可证明的顺序等本机事实，在该设备加入时补充。未设置不覆盖已有备注，显式清空参与合并；未知历史顺序不虚构。本机独有资料还需补齐引用，避免加入已删除歌单的成员时生成孤立记录；必要时作为整组恢复候选保留。

一次性合并应在同一事务中落库：已验证远端状态、待发布增量、业务视图和按目标/安装/域隔离的导入回执。候选未解决时保留冻结输入，不标记合并完成。合并时本机或远端发生新编辑需要重基或重新预览，不能用旧冲突选择覆盖新候选。上传失败重放原计划，不再次制造原创操作；已完成的输入不重复导入。

统计也只合并本机自身来源的未覆盖贡献，按原 source/revision 去重。不能把设备缓存的全账号总量作为自身新增时长累加；bootstrap 已纳入的来源再次加入不重复计数。v2 启用后不以旧统计目录持续读取作为兼容桥；独立统计协议升级必须满足同一分轨边界。

所有仍需使用的设备更新、完成自身合并/同步并解决真实冲突后，会通过同一 v2 因果状态收敛。不需要设备同时在线，没有七天等待或设备管理前置条件。未更新设备上的新资料在其更新前不进入 v2；官网明确提示全部设备更新并保留本机数据。

### 4.4 设备管理与迁移分离

连续 7 天无同步活动标记休眠，用户可停用不再使用的其他设备；状态仅用于设备管理，不决定是否可迁移，也不授权删除墓碑或历史数据。重复下载相同来源不得刷新活动时间；无法确认的时间明确标记未知。停用旧设备不能阻止其持有旧凭据继续写 v1，对应设备更新时仍须按其本机资料处理冲突。

界面显示“正在优化同步”或“增量同步已开启”等结果，不显示等待所有设备上线，不增加正常迁移确认弹窗。只有真实业务冲突沿用冲突处理。统计协议独立升级，见第 10 节。

```mermaid
flowchart LR
  UI[共享界面与原生播放事件] --> TX[SQLite 业务事务与 outbox]
  TX --> S[共享 Rust 调度器]
  S --> P[本机增量批次]
  P --> O[WebDAV 不可变对象]
  O --> H[最后发布本设备不可变提交记录]
  H --> R[其他设备发现版本变化]
  R --> M[补齐缺失前缀与因果合并]
  M --> DB[事务提交因果状态和业务视图]
  DB --> UI
```

分成三个独立域，分别安排优先级与序列：

| 域 | 数据 | 原则 |
| --- | --- | --- |
| library | 歌单、收藏、关注/分组、关联清单、用户资料覆盖、歌词选择与偏移 | 低频、高价值；事务边界内完整变更；并发冲突保留 |
| progress | 已启用同步的最近播放、歌曲/合集断点 | 高频、轻量；只保留必要记录；绝不触发 library 上传 |
| statistics | 每统计来源的时长与有效次数 | 来源独占、累计替换、不重复计数；独立暂停与升级 |

library 内部同一批次可覆盖多个实体，避免每种记录各建文件。可选 progress 不混入 library；关闭进度同步不会生成“删除远端全部历史”的操作。

### 5.1 远端目录

```text
BiliMusic-sync-v1/<uid>/                   # 原 v1 保留
  sync-v2/<vaultId>/
    bootstrap/genesis.json               # 固定协议身份；数据由各 actor 检查点提交
    control/<actor>/<generation>-<hash>.json # 不可变 head 提交记录
    manifests/<actor>/<domain>/<hash>.json
    objects/<actor>/<domain>/<hash>.json.gz
```

沿用原应用父目录，减少授权迁移。所有对象都带 schema、vaultId、uid/账号范围、domain 和 actor 校验；内容哈希只验证完整性，不提供用户认证、端到端加密或抵御持有云盘凭据者的篡改。

每个 actor 只能写自己的 control 子目录与对象路径。没有共享可变全局 manifest，没有云端主节点选举。通过缓存 actor 列表和按 actor 列举 control，发现有效最大 generation；不递归扫描所有对象。manifest 和对象按引用直接获取。

**head 采用不可变提交记录，而非反复覆盖一个文件。** 单写者仍可能遭遇“旧 PUT 超时后在服务端晚完成，覆盖新 head”。因此提交文件名包含 generation 与内容哈希；迟到的旧写只增加一个旧代记录，不会覆盖新代。客户端按最大合法 generation 选择，持久化已确认水位拒绝回退；同代不同哈希视为分叉。可变 latest 指针至多作为将来的性能提示，不能成为正确性的唯一入口。

控制记录只由原 actor 回收。确认新提交可列举和读取后，至少保留最近 8 代及全部本机在途代，每 16 代尝试清理；删除更早 marker 不代表删除它覆盖的语义状态。旧读者遇到缺失 marker/对象重新列目录。数据对象仍按第 8 节保留代际与宽限期。崩溃可留下更多 marker，恢复后有界清理；服务端迟到旧写重新出现也不改变选代规则。

这里依赖普通 WebDAV 成功存储最终能被 GET/目录列举看到，不依赖条件写互斥或同一 URL 的超时请求完成顺序。若目录暂缺或回退，保留已确认状态、退避刷新；不能证明完整目录时不执行破坏性 GC。

### 5.2 head、manifest 与批次

head 保持小型 JSON，含 `schema, vaultId, seedHash, actor, generation`，以及各 domain 的 `{selfSeq, manifestHash}`。普通探测列举控制元信息，只读取新提交记录；某域哈希没变就不读取该域 manifest。

manifest 为不可变文件，包含本域最近检查点引用、连续 tail 批次引用、对象长度与编码。每个批次用 `firstSeq, lastSeq, hash, compressedBytes` 标识。检查点覆盖向量放在 manifest/检查点中，不让所有大向量反复进入 head。

```json
{
  "schema": 2,
  "vaultId": "example-vault",
  "seedHash": "sha256:...",
  "actor": "example-installation-actor",
  "generation": 17,
  "domains": {
    "library": {"selfSeq": 83, "manifestHash": "sha256:..."},
    "progress": {"selfSeq": 246, "manifestHash": "sha256:..."}
  }
}
```

示意数据不作为真实 UUID/哈希校验样例。编码中用 actor 字典、字段枚举和批次级共享 context 减少重复；解码后仍须恢复同一因果事实。

批次传递可合并的 delta-state，而非可重复相加的命令。例如“这个字段在 dot=(A,84)、context=C 下赋值为 X”，而非没有上下文的“把歌单名改成 X”。每批携带精确 `dependencies`（本域因果依赖连续前缀）及种子标识；接收者先满足依赖，再原子应用整批。跨域事务首版不做网络原子性承诺，library 内的多实体操作必须同批完整呈现。需要原记录恢复信息时，把当前 `__record` 等价信息压到本次实体变更中，不能直接删掉这一语义。

现有 `Doc.join` 是完整状态合并，不能将它用于“只截取几个字段”的包并假定就是正确的 delta-CRDT。新因果核须定义 delta、覆盖上下文及依赖交付规则，并通过第 15 节测试；完成前只上线阶段 A。

## 6. 因果状态与业务规则

### 6.1 必须保持的不变量

1. 同一 actor/domain 序列单调、不复用；本机业务修改、序列分配与 outbox 同一 SQLite 事务提交。
2. 网络交付允许重复、乱序、中断；合并满足幂等、交换、结合，重复发送不改变结果。
3. `confirmed_frontier[actor]` 表示已原子纳入状态的**连续前缀**，不是见过的最大序号。
4. 因果上下文与传输完成前缀分开。当前 `Doc.clock` 不能直接用作下载游标。
5. 删除事实不因检查点或压缩丢失；过期副本不能复活已因果删除的记录。
6. 接收远端变更不会产生新的本机操作，避免回声传播。
7. 接收合并不能覆盖本机未上传修改；确认上传只覆盖本次实际提交的序列前缀。
8. 跨账号、同步目标或 vault 的内容与缓存完全隔离。

### 6.2 按数据类型合并

| 数据 | 合并规则 |
| --- | --- |
| 歌单名、备注、资料覆盖、歌词选择/偏移 | 因果后继覆盖；真正并发的不同值保留多值冲突，不用设备时间静默丢弃 |
| 歌单成员、收藏、关联清单 | 延续当前删除优先展示与因果删除语义；显式重新加入创建新的存在事实并携带已见删除上下文 |
| 删除与离线旧编辑并发 | 不因修改普通字段而隐式重建；保留可恢复候选。普通 edit 不发送新的存在性 add，只有显式重新加入才发送 |
| 歌单排序 | 首次传输升级沿用现有逐成员位置和冲突语义；发送实际变化的位置字段 |
| 播放断点 | 因果后继优先；并发会话保持各端候选，按确定规则给默认值并允许恢复；不能取最大秒数，主动回听也必须成立 |
| 听歌累计 | 每来源独立；同一计数单元取较新累计状态/最大合法累计，不把重发包当新聆听 |

排序的分数索引/LSEQ 是独立语义升级：只有重排流量在基准中显著占比时再引入，同时验证相同间隙插入、并发移动及索引变长。先避免同时更换传输、集合语义和顺序算法。

删除规则有一项明确收紧：v1 的 `Doc.update` 会为普通记录编辑重发 `__present=true`，v2 将“编辑”与“重新加入”分开。恢复候选继续保留；这项行为差异需迁移说明与专项回归，不宣称完全沿用旧实现。

### 6.3 写入身份与恢复

资料库使用数据库外安装标识，并绑定数据库实例与 actor；参照现有统计来源的安装隔离，但额外检测序号回退和 head 分叉。

本地互斥锁防止同一安装两进程同时写同一个 actor。恢复旧备份、复制数据库、安装身份丢失或发现同序号不同哈希时，保守轮换 actor，旧 actor 只读。序列高水位与恢复标记持久化在不随普通资料导出复制的安装状态中；两个存储间的崩溃不确定状态允许多生成一个 actor，绝不复用一个可能已发布的 dot。

旧 outbox 先按远端确认前缀核对：已发布的不能重新换身份发布；无法确认的恢复修改放入待恢复区，与远端重基后预览处理。统计来源沿用原身份，只由确认为原安装拥有的来源继续写，不把旧累计改名成新来源。

### 6.4 因果核的最小定义

每个逻辑寄存器 k 表示为 `(Ck, Vk)`：Ck 是已经观察到的 dot 集合，Vk 是尚未被覆盖的 `(dot, value)` 候选。dot 的命名空间包含 actor/domain/seq，寄存器键参与定位；一个业务事务可在同一 seq 下修改多个不同寄存器。相同寄存器与 dot 的不同值属于非法分叉。

两个**完整寄存器状态**合并为：

```text
C = C1 union C2
V = (V1 intersect V2)
    union { x in V1 | dot(x) not in C2 }
    union { x in V2 | dot(x) not in C1 }
```

这里的集合交按 dot 与相同值判断。新赋值产生 fresh dot，并使本次已观察候选进入覆盖上下文；并发、未观察的候选继续保留。存在性也是寄存器，若并发候选中有删除，先显示删除；显式重新加入必须观察已有删除再创建新存在值。普通字段修改不修改存在性。

delta 的上下文只作用于它明确携带的寄存器；不能将批次共享上下文当作“所有未出现字段都已删除”。编码可以共享 context 的字节，逻辑解释仍逐寄存器。Ck 用区间/连续向量加例外 dot 压缩，只有证明不存在缺口时才能简化为一个最大 seq；未出现字段、值 null、空字符串和删除是不同语义。

此定义给出基本寄存器的半格合并边界。实体恢复、引用清理、排序投影以及多寄存器批次因果交付还要单独验证，不因寄存器公式正确就跳过集成测试。

### 6.5 本地持久状态

新增有序 SQLite migration，至少包含：`sync_actor`（身份/epoch/下一序列）、`sync_outbox`（domain/seq/frozen bytes）、`sync_registers`（confirmed 因果状态）、`sync_frontier`（连续已应用前缀）、`sync_object_cache`、`sync_publications`（在途提交计划及确认）、`sync_traffic_attempts`（预占与结算）。

仓储操作接收事务上下文与 `origin=local/remote/migration`。local 写业务视图和 outbox，remote 写 confirmed 状态并刷新视图、不会再次排出站；migration 按确定规则产生种子映射。业务原来的 SQLite 视图和 UI 查询继续使用，避免让前端直接理解 CRDT 文档。

## 7. 一轮同步与故障恢复

### 7.1 本机写入和上传

1. 用户操作立即完成本地事务：业务视图 + typed delta + actor/domain seq + outbox；不等待网络。
2. 调度器冻结本轮 `publishThrough`。批次、哈希和本轮待发布 manifest/head 在本机持久化；后续编辑进入下一轮。
3. 上传不可变 delta 对象，需要压缩时先上传检查点；重试使用同样路径与字节。
4. 上传不可变 manifest，确认所有引用对象都已成功上传。
5. 最后 PUT 自己的不可变 head 提交记录。这是本机本轮的远端发布点，不是所有设备的全局事务。
6. 成功响应后事务性确认对应前缀：把已确认本机 delta 纳入 confirmed 寄存器与 frontier，再清理该前缀的 outbox/overlay，不能只删除待发送记录。若响应丢失，GET 本轮精确提交文件判断是否已提交，再列举当前最大代检查分叉；结果不明时保留 outbox，重试同样字节。旧请求晚完成不会覆盖较新代。

读取他端数据与发布本机 delta 可独立推进；应用本机编辑时已保存其基于的因果上下文，不需要先在线拉取才能写。发生冲突的字段可保留待处理，不能阻断统计和其他独立字段传播。

### 7.2 远端读取

1. 从 control 发现新 actor，检查每个 actor 的提交元信息；有效最大 generation 变化才读取对应提交记录。根 actor 发现可低频运行，进入音乐库和手动同步立即补查；不能只永久缓存已知 actor。
2. 读取变化 head 和对应域 manifest，用本机连续前缀定位缺失区间。
3. 需要的批次先下载落临时文件，验证哈希、尺寸、身份、序号、domain、dependencies 和编码，再做合并。依赖未满足则补前缀或检查点，出现非法依赖循环/未知种子时拒绝，不推进游标。
4. SQLite 同一事务写入 confirmed CRDT、业务投影、已接收对象与连续 frontier；本机 outbox 作为 overlay 重放，保持界面新编辑。
5. 不把收到的 delta 再以本机新序号发布。若对方 head 后续又有变化，下轮补齐。

缺失前置依赖时，按 manifest 的 covered frontier 补对应 actor 缺口，或用自包含检查点恢复；不能先跳过缺口再推进游标。任何阶段切账号、暂停或换目标都取消任务，并在提交前复核 account generation。

### 7.3 明确的恢复动作

| 情况 | 动作 |
| --- | --- |
| 对象上传成功，head 尚未提交 | 远端暂不可见；重试原对象与 head；不丢 outbox |
| head PUT 成功，响应丢失 | 读回 head；确认原 manifest 或已确认继任，再清理前缀 |
| 读到旧 head，引用对象已经回收 | 抛弃这次远端计划，强制重读当前 head，必要时下载检查点；404 不等于空库 |
| head/manifest 暂时损坏或部分可见 | 保留上一份已验证状态，退避重试；不传播删除 |
| 304 但缓存不存在/损坏 | 无条件重读，再验证；不得继续使用空数据 |
| 同 actor、同序号、不同内容 | 报告分叉并轮换身份；保留双方数据供恢复 |
| 目录被用户清空 | 不能把整体消失当逐条删除；提示恢复/新建库，禁止无条件认领新 epoch |
| 云盘返回旧 head/迟到 PUT | 选择当前可验证最大不可变代，不回退已确认的 generation/frontier；目录持续回退则提示恢复，不覆盖本地 |

## 8. 检查点、压缩与回收

检查点是**完整、自包含的合并 CRDT 状态**，包含存活值、冲突候选、删除墓碑与上下文，以及实际纳入的连续 covered frontier。普通最终 `Snapshot` 只适合展示/导出，不能替代它。

只有本机日志达到压缩阈值时才生成，不因收到其他设备的变化生成。最简单的安全流程：对 confirmed 状态生成检查点，本次未确认 outbox 继续作为 tail；如果将待上传变化纳入检查点，head 必须同时确认那个精确前缀，且状态构造不得漏掉前缀内任何事务。

检查点含远端已合并状态的字节，不引用别人可能回收的旧日志。因此每端可独立用自己的新检查点替换自己的日志前缀，不依赖全设备在线或全局共识。

初始策略：manifest tail 达 32 批或累计压缩体积大于 `max(256 KiB, 上次检查点体积)` 后，下一次本机发布时压缩；24 小时只是有待压缩日志时的检查机会，无变化不生成检查点。持续增长时按域压缩，不扫描音频缓存。

当前实现先上传检查点及新 manifest，再发布 head 并读回确认，只清理过期控制 marker。不可变数据对象、manifest 和墓碑保留，冷恢复不依赖其他设备在线。以下 GC 规则是后续空间回收的安全约束，尚未启用数据对象删除。

本机持久化的在途 manifest 和其引用对象也属于 GC 根，不能被当成孤儿删掉。崩溃后恢复发布前，重新验证或幂等重传所有引用，不能仅凭崩溃前的内存标记认定对象仍存在。冻结的 generation、manifestHash 和批次字节须先落盘再联网，同 generation 不得改指其他内容。

GC 标记从**全部保留提交记录引用的完整 manifest/object 图**及在途计划出发；只有不再被任何保留根引用、满足宽限期的对象才可回收。不能保留四代控制记录，却只保护两代控制记录引用的对象。

墓碑回收与日志回收完全不同：首版长期保留紧凑因果删除标记，不因 90 天无人上线就删除。需要缩减长期 actor/tombstone 元数据时，必须显式设备退役及协调重建新 vault；旧设备经重新加入和修改恢复流程进入，不能直接重放旧身份。普通标量覆盖可丢弃已被因果覆盖的旧候选，仍须保留必要覆盖信息。

冷启动先读取全部小 head/manifest，优先选择“覆盖较多前缀且体积较小”的有效检查点，再补缺失 tail；能证明已覆盖某 actor 的提交前缀时跳过其大对象。不能仅凭时间戳选所谓最新检查点；最坏情况下仍需读取多份检查点。

### 8.1 编码

首版使用确定性紧凑 JSON + gzip，复用现有 `flate2`，gzip mtime 固定为 0；字段顺序、整数编码与 null/缺失语义固定。对象 SHA-256 基于实际传输字节；相同冻结批次重试必须复用原字节。换库/压缩版本可能产生不同压缩字节，不能仅靠业务等价假设哈希相同。

小于 512 B 的对象可以不压缩，编码写入引用元数据；大批次再压缩。比较 gzip 不同等级，以及 [CBOR](https://www.rfc-editor.org/rfc/rfc8949.html)/zstd 后再决定是否增加新依赖和解码能力。不能把“JSON 换二进制”当主要省流来源。

最初限制：head 16 KiB、manifest 32 KiB、单 delta 解压 256 KiB、检查点解压 32 MiB；checkpoint 分片和更大资料库支持需后续明确协议版本。所有读取流式限长，先验压缩长度再限制解压总量与记录数，避免解压峰值占用播放线程。数值为设计上限，不改现有业务条目配额。

## 9. 缓存、目录与请求控制

缓存键至少包括规范化 endpoint、provider、uid、凭据主体标识、vaultId、protocol、对象路径和编码；不保存或输出明文密码。切换账号/目录/凭据主体后旧缓存不能被新目标引用。

v1/v2 目录请求 `getetag/getcontentlength/getlastmodified/resourcetype`，按返回 href 严格限定目标目录与文件名。分页按实际提供商能力实现，不能以“返回不足上限”证明没有后续文件；对象区不靠递归 PROPFIND 发现。

可用 ETag 时：元信息未变直接复用缓存，或条件 GET 得到 304。提供商缺少 ETag 时，以小 head 为探测对象；v1 不可靠元信息模式保留有界的周期性完整校验。长度+mtime 只作提示，不能作为永远跳过内容的证明。发现 ETag 固定、回退或内容不匹配后降级；v2 无条件获取小 head 的成本仍然可控。

首次“连接并预览”保持只读；不为能力探测偷偷创建远端文件。使用已经授权的实际上传学习服务行为，目录存在缓存遇到 404/409 时再修复。

同目标复用 HTTP 连接池，初始限制 GET 并发 2、PUT 并发 1；手动与本机编辑优先。429 尊重 Retry-After，网络失败采用 full-jitter 指数退避，1 秒起、上限 15 分钟；批次重试保持幂等。不绕过系统证书校验，不跟随携带授权头的跨域重定向。

坚果云官方同时限制[免费账户每 30 分钟 600 次 WebDAV 请求](https://help.jianguoyun.com/?p=2064)，所以小包数也必须受控。后续可增加逐请求 token bucket，预留交互/恢复额度，未知活跃设备数时保守按已注册设备分摊预算；全账号仍可能有其他应用，429 是最终反馈。不能只控制单设备并发就当作控制账号限频。

## 10. 播放进度与统计的专门优化

### 10.1 播放进度

本机仍按原生播放器节奏写 SQLite；网络只提交已启用同步的轻量域。保留最近 200 首和必要合集断点，不同步当前播放命令，避免同步触发其他设备自动播放。

“最近 200 首”是合并后的物化视图上限，不把本机列表外条目的缺席转成全局删除。真正回收旧 progress 因果事实需要独立的过期屏障，首版不凭本机 top-200 清除远端因果状态。

同一曲目在尚未进入因果日志之前，可合并采样为本轮最新断点；已经分配和持久化序号的条目不能直接删掉造成序列缺口。可在本地 `pending_progress` 可覆盖槽中聚合，再按网络提交事务生成一个 delta。

聚合槽保存采样发生时的会话和已观察因果上下文，不能套用后来收到的远端上下文，否则旧本机样本会伪装成远端进度的后继。并发候选优先显式 seek/暂停/选曲，再比较已校验的观察时间、actor、会话内序列；因果后继优先于这套并发排序。时间偏差大时保留候选提示，手动选择生成观察所有候选的新事件。

暂停/切歌请求尽快补发，默认最小上传间隔 30 秒，连续播放约 60 秒一次；切后台立即本地保存，只有系统执行窗口允许时尽力上传，不阻塞退出。主动跳到较小进度也是有效变化。

高频小断点采用可选的**内联热 tail**：提交记录中直接携带自有 progress 检查点之后的连续小批次，阈值 4 KiB 或 32 批，避免每分钟都 PUT 对象和 manifest。新提交必须带齐未检查点覆盖的自身前缀；达到阈值先上传自包含 progress 检查点，再从空 tail 开始。重复内联数据由 frontier 去重。较大进度集仍用外部 manifest，不让控制记录超过 16 KiB。这样用少量重复字节换更少往返，是否默认启用由同轨迹对照决定，不能把只含最后一个断点的 head 当完整历史。

### 10.2 听歌统计

先保持当前成熟的独立来源、gzip 月包、revision 和 ETag，仅消除重复目录创建/自有索引下载，并对 force 做最小间隔合并。资料库 v2 的发布不强迫统计同时换协议。

如果基准表明月包已成为主要流量，再推出独立 `statistics-v2`：

- 每个来源只发布自身贡献。用整数毫秒和整数次数，旧浮点累计一次性转换且保留迁移总量，误差不逐包扩散。
- 同次采样更新相关累计单元属于同批事务，不能远端只见一半投影。旧版各单元分别舍入到最近毫秒，记录摘要及各投影的舍入差；每单元误差不超过 0.5 ms，不能为强凑总量改写旧来源。迁移后新采样由规范化整数时长派生各投影。
- 使用来源独占的累计单元，如 `(source, month, track)->ms/plays`、`(source, day)->ms/plays` 和最近 90 天 `(source, day, track)` 明细。一次采样更新相关单元，批次只发送有变化单元的**绝对累计值**；同来源同单元幂等取合法新累计，不上传“加 15 秒”这种可重复相加命令。
- 月排行只汇总月单元，日历只汇总日单元，不能把两套投影再相加。同来源不同版本也不能相加；不同来源才累加。
- 离线补报旧日期是合法更新。统计迁移种子与 v1 已确认源 revision 精确对应，只表示同一笔贡献一次；阶段切换后不同时累加 v1/v2 两套结果。
- 每来源保存不可变的权威协议与 cutover revision 映射。混合升级可继续全账号使用 v1，或逐来源切换权威协议，不能把整个 v1 汇总与整个 v2 汇总相加；重装和更换库也不能重置映射。
- 冷月累计进入自包含检查点，热变化留在小批次；不为每首歌创建一个远端文件，也不把整月所有歌曲放入每次热包。
- 90 天明细仅影响可查询的细分投影，永久月/日累计不减。检查点裁剪须保留已覆盖前缀与过期明细屏障；旧检查点带回的细分字段不能重新变成有效新数据。首版可以只在展示层过滤明细，正确性优先于立刻回收每个字节。

这是专用 G-counter 式来源累计设计，不是无来源的全局计数器。若按轨迹比较后省流收益不抵请求数、迁移复杂性和文件增长，继续沿用 v1 月包。

## 11. 自适应调度

调度状态与失败退避移到共享 Rust，React/Swift/Kotlin/ArkTS 只报告 lifecycle/网络提示。进程内用单调时钟；持久化失败次数和有界剩余退避，重启重算 deadline，不能复用上次进程的 monotonic 数值。UTC 时间只作重启提示和日历依据，时钟跳变不得导致无限等待或无限重试。

| 场景 | 初始策略 | 边界 |
| --- | --- | --- |
| 修改歌单、收藏、备注 | 2 秒合并防抖，最晚 10 秒进入提交队列 | 联网、未限流、预算允许且进程获执行时成立；不表示 10 秒完成网络或其他端可见。最大等待从首条待处理操作计算 |
| 批量导入 | 结束、累计 256 操作或 64 KiB 原始 delta 时封批 | 一个业务事务不在包中切成半个可见事务 |
| 已知远端正在变化 | 下次检查 30 秒，之后 1/2/5 分钟 | 只查控制信息，增加约 ±10% 抖动 |
| 正在浏览音乐库 | 远端检查约 1～2 分钟 | 能见度要求高于纯播放 |
| 无编辑、纯播放 | 远端资料探测逐步退到 10～15 分钟 | 本机修改/断点上传独立，不等空闲轮询 |
| 回前台/网络恢复 | 距上次检查至少 30 秒才补查 | 多个事件合成一轮；手动除外 |
| 统计 | 保持 15 分钟；打开统计页超过 30 秒可补查 | 先不增加默认上传频率 |
| 手动立即同步 | 跳过普通等待，处理各域一次 | 仍尊重服务端限流和同目标单飞 |
| 手机后台 | 本地持续记录，联网尽力提交 | 没有系统执行窗口时，下一次前台补齐，不承诺后台时限 |

队列按用户手动、dirty age、域优先级、deadline、估计字节安排；同账号库的网络 I/O 永远不占用播放账号锁或长时间 SQLite 锁。

可见性分两段：发起端提交延迟与接收端发现延迟。默认空闲设备可能要等到下一轮 10～15 分钟检查；用户打开音乐库/点击同步可加速。如果需要后台即时推送，必须另建可信服务或系统推送通道，不属于纯坚果云方案。

## 12. 流量模型与预算

令 D 为云端设备文件数，H 为所有设备每日前台小时数之和，P 为每小时检查次数，S 为单设备完整传输文档大小。当前资料库月下载主项为：

`B_v1 ≈ 30 × H × P × D × S`，当前 P≈20；变更事件和前台恢复另计。

v1 缓存模式：完整载荷只在远端文件变化/缓存失效时下载，主项从轮询次数转向变化次数，但跨端完整状态再发布仍可能放大。

v2 稳态把“全库大小 × 轮询”改为：

`上传 ≈ 本机原创变更批次 + 自有检查点 + manifest/head`

`下载 ≈ 未拥有的原创批次 + 必需检查点 + 控制信息`

每条唯一编辑通常只发布一次，其他 D−1 台最终接收一次。所有端都需要知道变化时，至少要向这些接收端传达足够的信息；不能承诺传输量完全不随设备数增长。v2 主要去掉轮询整库和接收回声，并非消除这个下界。

请求数和控制头同样记入成本，不能只比较压缩正文。小包过碎时，合批比继续压缩更重要。自动选择“缺失 tail / 检查点+tail”以估计传输量与 RTT 成本较小者，但只在两条路径都包含完整必要因果状态时比较。

### 12.1 计量

统一 transport 按每次尝试记录：域、方法、状态、时长、发送体估计、已接收字节、重试、是否命中缓存。收到半包失败也计下载，不只成功回合计量；鸿蒙桥接返回同类计量信息，Base64 只在本机桥接不算云盘流量。

上传失败时不一定知道服务商收到多少，使用“计划完整请求体”的保守估计并标记不确定；HTTP/TLS 开销与服务商账单可能不同。界面区分本机估计、已知其他设备用量和用户校准的坚果云余额。

计费周期可配置，不硬编码自然月；按用户分给 BiliMusic 的额度预算，不假定整个 1 GB/3 GB 都能用。可设 70% 提醒、85% 降低空闲探测、95% 暂缓自动大包和首次恢复。每请求在 SQLite 事务预占估计额度，再结算确定字节，失败上传保留保守预占，避免并发各自认为余额足够。达到本机分配上限后暂停全部自动传输；手动解释预计体积后可以覆盖一次，数据一直保留本地。

没有服务端协调器时无法精确执行全账号硬预算：其他软件、离线设备、旧客户端都不可见。多端可分配各自上限并预留余量；这种上限只约束遵守协议的新版实例，不能冒充坚果云账单。

### 12.2 本次成本模型结果

配套的 `docs/sync-traffic-model.py` 是可复现的估算器，不访问用户资料、不连接坚果云、不实现或验证同步正确性。模型比较固定假设下的载荷和请求开销，初始种子/恢复与失败重试另计。

模型默认每端每天前台 2 小时、每份旧文档 500 KB；每端每日 30 个压缩后 1 KiB 的资料批次、120 个压缩后 256 B 的断点批次，两个域每日检查点共 144 KiB。假设所有接收端下载所有新提交，而非跳过中间代；每 3 分钟检查全部 actor 控制目录，每目录留 4 个提交记录，head 1 KiB、manifest 4 KiB，请求/响应开销分别估算 1 KiB。列目录、自有提交读回、marker 清理也计成本，不假设 metadata 免费。

| 设备数 | v1 月下载估算 | v2 外部批次月上传估算 | v2 外部批次月下载估算 | 下载减少 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 602 MB | 55 MB | 34 MB | 94.3% |
| 2 | 2,407 MB | 141 MB | 164 MB | 93.2% |
| 3 | 5,415 MB | 258 MB | 389 MB | 92.8% |
| 5 | 15,037 MB | 582 MB | 1,125 MB | 92.5% |

同样 3 分钟探测频率下，3 端完全无编辑场景约从 5.4 GB 降到 43 MB（只剩控制请求估算），完整资料正文为零。相反，旧文档只有 100 KB、manifest 达 16 KB 时，3 端活跃场景仅从约 1.09 GB 降到 715 MB，说明复杂协议在小库上未必划算；必须与阶段 A 强基线比较。

以上不含听歌统计、初次恢复、设备一次性加入、TLS、对象回收和失败重试；也未计 ETag 命中、跳过中间代及内联 tail 的进一步收益。v2 对象尺寸需由编码实验替换，不能当真实用户流量承诺。旧库上传只给“每轮都发布”的情景上界，不作为现状平均值。

外部批次场景 3 端共约 16.5 万请求/月；若所有操作都集中在每天相同 2 小时，平均超过每 30 分钟 600 次，尽管字节已节省仍不合格。因此应结合合批、跳过过期提交和请求预算；当前已合批和发现最大提交，逐请求预算仍是后续扩展；受限时降低断点提交频率，保留用户编辑优先。这个模型有意暴露纯小文件增量方案的不足，不将它直接作为默认上线参数。

复现与敏感性比较：

```sh
python3 docs/sync-traffic-model.py
python3 docs/sync-traffic-model.py --devices 3 --library-batches 0 --progress-batches 0
python3 docs/sync-traffic-model.py --devices 3 --document-kb 100 --manifest-kb 16
python3 docs/sync-traffic-model.py --json
```

A 阶段可逐项回退到 v1 完整 GET；缓存损坏不影响云端格式。B 阶段只能保留原 v1 和导出备份进行有意识的回退，不能降级程序后让旧引擎写 v2 数据。

## 15. 实验与验收

先测当前基线和 A0 正确性修复后的强基线，再逐项增加机制：v0.3.1 → A0 → 仅缓存/ETag → 独立脏区与调度 → 分域 v2 增量 → 检查点 → 可选统计/编码。重放同样操作、故障种子与网络时延，避免把“轮询变慢”或修掉兼容循环造成的收益都当作增量算法效果。

负载：1/2/5/10 设备，100/1,000/5,000 首，1/10/100 歌单；无编辑、只播放、30/300 次日编辑、批量导入、交替离线修改、30/180 天离线恢复、移除旧设备。其他条目超过现有业务配额时作为独立扩容实验，不能直接生成无效基线。

测量：完整收发体积、请求数、首恢复体积/耗时、单次编辑传播 p50/p95、失败重试量、压缩 CPU/峰值内存、SQLite 锁时间、播放事件延迟、对象数/长期墓碑增长。ETag 命中率和重复发布率分开报告。

决定性正确性用例：

- 合并的幂等/交换/结合；不同顺序最终状态与冲突集合相同。
- 重复、乱序、丢失、部分可见、任何上传或事务边界崩溃后恢复；旧请求超时后服务端晚于新代完成仍不丢发现入口。
- 已删除条目被长期离线设备编辑；删除与显式重新添加并发。
- 检查点 frontier 恰好边界、序号缺口、跨域依赖、旧 head + 已回收对象。
- 快照只含最大 seq 却漏掉中间操作必须拒绝；同序号不同哈希必须检测。
- 上传时继续编辑，只确认 publishThrough；远端检查点不覆盖本机 outbox。
- 数据库复制/恢复旧备份、actor 回退、两进程、账号与目标切换。
- 相同 provider 换目录/远端主体不复用旧基准；密码轮换仍识别相同目标。历史 schema 升级、崩溃恢复和未来版本保护。
- 歌词删除、覆盖清空、缺失/null 的 apply/export 闭环；重复输入不改排序、不生成 outbox；非同步本机内容保持。
- ETag 缺失/固定/回退、304 缓存缺失、403/429/配额失败、超限压缩包。
- 鸿蒙路径/MIME/字节桥接；WebView 销毁后本机记录保留。
- 统计月末、跨天、迟到更新、原生后台换曲、迁移重读均不重复累计。
- 首台新版在其余旧设备在线、离线或活动时间未知时均可迁移，前提是已发布云端来源完整通过校验。
- 两台首次升级设备共享确定性 genesis；发布顺序、掉线重试、旧 v1 PUT 晚完成均不分裂库、不伪造新贡献。
- 只有初始化检查点也可被后来设备完整恢复；普通接收不产生上传回声。
- 初始化上传期间新增编辑仍留在 outbox，确认检查点不删除其批次。
- 后来升级携带本机输入：已上传 v1 但未进入 v2 的修改不能因与旧基准一致而遗漏；没有因果证据的差异保留冲突。保留本机备注/顺序。
- 只剩墓碑、只有关联清单的已发布来源也要校验；休眠或停用不删除来源事实。
- 已加入新版不再发出任何旧目录请求；旧设备升级时一次性合并按原身份去重，不能复活 v2 删除；统计按自身来源去重。
- 并发名称修改、删除/修改、缺失/null、缺失基准均保留可处理候选；选择后重复导入不重新制造冲突，所有新版按不同接收顺序收敛。
- 正常迁移无需点击确认、无需等待离线设备；网络故障重放相同计划。
- 首次连接预览只读；断开目标或全部同步关闭后零同步请求，仅暂停资料库时允许独立统计继续。

性能放行：无编辑稳态完整资料载荷 GET/PUT 为 0（缓存修复除外），只更新断点不上传 library，单曲新增只传所需记录、合并后不再次原创发布，旧缓存恢复不需下载全部历史。若这些未成立，不用压缩比掩盖问题。

每台设备的最终活跃轮询延迟、请求开销与真实坚果云压缩/MIME/ETag 行为均需实测。对外只给固定场景的测量结果，不保证所有用户每月一定小于某个 MB 数。

## 16. 实施前需固定的工程决定

已固定：本机模型治理、历史兼容修复和 v2 执行器一并交付；首台新版完整校验已发布 v1 云端数据后直接建立 v2，其他新版更新时一次性合并本机资料，之后只使用 v2，无需等待所有设备或用户确认，不持续读取旧云数据，也不回写 v1；因果冲突与排序延续，普通编辑与重新加入显式区分；JSON+gzip 首发；统计已接入 v2 累计单元同步；进一步编码优化独立评估，遵守不再读取旧目录的边界；Rust 单一引擎；不增加手机常驻同步服务。

尚需通过小实验收敛的参数：检查点频率与 tail 上限、批次大小、热/闲轮询间隔、缓存配额、冷恢复选择启发式、head/manifest 实际尺寸。新因果核必须经属性测试与有界状态穷举/模型检查；本设计审查和成本估算不替代实现正确性证明。
