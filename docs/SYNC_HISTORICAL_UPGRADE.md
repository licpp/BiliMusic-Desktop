# 历史版本的 V2 同步升级与回退

0.3.2 和 0.3.3 的本地数据库版本为 4。新版可迁移这些数据库。回退到历史二进制时，需要从升级前保存的 SQLite 快照恢复本地数据，然后重新同步 V2。历史客户端会拒绝打开高于其支持版本的数据库。

## 重放测试

从仓库根目录运行以下命令。第一个参数是待验证的 Git 提交，默认取 `HEAD`。第二个参数可选，用来保存结果。

```bash
node scripts/test-sync-history.mjs HEAD artifacts/refactor-checkpoints/sync-v2-historical.json
```

脚本使用 Git 标签 `v0.3.2`、`v0.3.3` 和待验证提交，分别编译三份真实同步引擎。每份源码快照单独运行。共用的测试 WebDAV 只监听本机回环地址，SQLite 和写入者状态都在临时目录。

如需复用待验证提交的 Rust 测试程序，可在运行脚本时设定 `BILIMUSIC_SYNC_HISTORY_CANDIDATE_BINARY` 为本地输出路径。回放完成后，用该测试程序执行 `--skip sync::history_replay::replay --test-threads=4` 即可运行常规 Rust 测试。

每个历史版本都独立完成以下步骤。

1. 历史客户端创建 SQLite，发布一份 V2 歌单，再写入一份尚未上云的歌单并保存升级前快照。
2. 新客户端以原数据库继续同步，在已存在的 V2 资料库发布原歌单改名及未上传的旧端歌单。
3. 历史客户端拒绝已经迁移的数据库，测试确认数据库文件哈希未改变。
4. 恢复升级前快照，历史客户端补收新端改动。同步引擎分配新的写入者身份并发布新的修改。
5. 新客户端重开升级后的数据库，接收旧端再次发布的改动。校验两份歌单及无冲突结果。

这项测试覆盖本地迁移、V2 的双向读写和恢复写入者身份。正式安装包的启动和数据库检查独立执行。客户端与坚果云真实账户的网络、认证及系统调度属于不同的验收路径。

本轮使用提交 `1dd91a2` 与两个历史 Git 标签执行重放。两组均通过上述五个步骤，确认历史改动、新版改动和回退后新增的修改可在同一份 V2 资料库合并。模拟 WebDAV 预建了 0.3.2 所需的目录，符合已有 V2 资料库的升级场景。

## 存档安装包核验

本轮本机核验使用存档的 0.3.2、0.3.3 和 0.4.4 macOS ARM64 正式镜像。三个应用均通过签名检查。两份旧版安装包分别在临时用户目录创建数据库，使用存档 0.4.4 升级后保留测试歌单。直接打开新版数据库时，两个历史应用均退出，数据库哈希保持一致。恢复升级前快照后，两个历史应用均能重新启动，歌单可读。数据库版本在两组测试中均为 4 → 13 → 4。
