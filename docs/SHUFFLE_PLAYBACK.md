# 随机播放

## 公开方案与取舍

Spotify 在 2025 年公开的 [Fewer Repeats 方案](https://engineering.atspotify.com/2025/11/shuffle-making-random-feel-more-human)会生成多个随机排列，按最近播放记录评价新鲜度，并选择更合适的顺序；其 Standard Shuffle 保留纯随机。Apple 的[公开说明](https://support.apple.com/en-us/109332)说明了随机与循环的操作方式，没有公开内部排序算法。

BiliMusic 采用有放回的逐次随机抽取容易反复抽到少数歌曲，而且过去的“上一首”按原列表倒退，与实际播放经历不符。这次采用无放回的随机轮次，并参考多候选排列与新鲜度评分。以下是本项目的具体规则，不代表复现厂商未公开的实现。

## 行为规则

- 一个轮次内每首歌曲自动播放一次。播完后生成下一轮，并避免轮次交界处立即重复当前歌曲。用户主动选择歌曲不受限制，该歌曲会从本轮待播列表中移除。
- 每轮生成四个 Fisher–Yates 随机排列。对前 128 首评分，近期播放的歌曲越靠前，惩罚越高；同歌手、同 BV 的相邻分 P 也有软惩罚。选择分数最低的一组，不排除任何歌曲，不使用热度或付费优先级。
- 新鲜度参考当前队列最近 50 次播放。它不是账号全局推荐记录，也不依赖云同步。
- “上一首”沿实际历史回退；再点“下一首”先重放向前的历史，再消耗待播列表。当前播放超过四秒时，“上一首”先回到当前歌曲开头，沿用原播放器约定。
- 历史最多保留 200 条。移除歌曲时清理对应历史和待播项；新增歌曲插入剩余待播项，元数据刷新、列表倒序不重置整个轮次。手动跳转会结束历史的向前分支。
- 关闭随机、切换账号或清空队列后重置。桌面端随本地队列保存轮次与历史；移动端由原生服务维持，WebView 重新创建仍保留同一原生会话，系统终止原生服务后重新生成轮次。
- 单曲循环、顺序播放与播放结束后的停止规则保持各自语义。随机模式会循环生成后续轮次。

## 跨端实现

`src/domain/shuffle.ts` 是纯策略模块，接受歌曲身份、歌手、BV 和可注入的随机数源。鸿蒙构建直接把同一文件复制成 ArkTS 源码，不维护算法副本。Android Kotlin 与 iOS Swift 保留无系统依赖的等价实现，以同一份 `tests/fixtures/shuffle.json` 验证状态演进。

桌面端在 `playerStore` 中使用策略。移动端的通知栏、耳机、后台结束事件和应用内上一首／下一首统一由原生队列选歌。前端等待正在提交的队列／模式更新完成后才发送切歌命令；失败回调校验操作和账号会话，防止旧操作覆盖新播放。旧原生驱动没有自主队列能力时继续使用前端策略。

随机状态只在设备本地使用，不上传账号统计或 WebDAV，不增加同步请求。

## 回归验证

- 100 个随机种子、80 首、连续多轮：轮内无重复、无遗漏，轮次边界不立即重复。
- 200 个固定种子的多歌手／多分 P 样例：评分排列的相邻聚集次数低于单次均匀排列基线，同时每轮仍覆盖全部歌曲。此结果是固定样例回归，不是对任意歌单的提升承诺。
- 共同 fixture 覆盖 70 次操作，包括轮次边界、历史回退／前进、手动选择、增删队列；TypeScript、Swift、Kotlin 核对同一结果。鸿蒙另测共享策略的原生队列调用。
- 覆盖本地恢复、错误快照、空队列、单曲、历史上限和重复元数据更新；播放器集成验证桌面恢复、移动端原生切歌与通知事件不回环。

```sh
node --test tests/shuffle.test.mjs tests/shuffle-native.test.mjs tests/player.test.mjs tests/ios-player.test.mjs tests/ohos-queue.test.mjs
node scripts/android-local.mjs test
```
