# 内容标题与合集信息

队列、歌单、歌词页与听歌统计共用内容名称。原始 BV 标题、原始分 P 标题、所属合集和用户改名分别保留；页面只决定辅助信息是否展示，不自行截断主标题。

## 显示优先级

1. 用户覆盖的标题优先，来源缓存不能替代用户选择。
2. 多 P 或已确认合集成员使用有意义的章节名；空值、P1、正片等默认名称回退到 BV 标题。
3. 已确认所属合集且标题重复合集前缀时，只在明确分隔或章节边界移除前缀。保留章节编号，不根据播放队列位置重编。
4. 有明确音乐展示包装且仅含一首引号歌名时，复用歌曲识别模块；普通书名、影片名和串烧不按此规则简化。
5. 缺少证据时保留可用名称，后台补全来源资料。

歌曲的辅助信息优先显示有效歌手；没有歌手时才回退到合集名，再回退到 UP 主。同一合集的队列顶部已经展示合集名，行内不重复合集名，但保留歌手。旧缓存中以 UP 主代填的歌手不算歌手证据；明确的手动编辑和导入歌单歌手即使与 UP 主同名也保留。歌单、队列、底部播放栏和听歌统计共用这一规则。歌词页保留现有合集入口和 UP 主入口，不重复添加系列行，没有歌手时不显示“歌手未知”。搜索同时包含原始标题、合集名称和内容名称。

## 数据与平台边界

- `domain/sourceTitle.ts` 负责前端派生显示；`domain/source_title.rs` 负责原生章节解析。两者使用 `tests/fixtures/source-title.json` 验证章节规则。
- `SourceTitleContext` 随本机 Track 快照保留来源上下文。SQLite V7 的 `source_title_cache` 保存公共来源资料，允许统计条目没有对应音乐库记录；它不进入个人同步协议，也不创建收藏、历史或统计。
- 旧版本资料按需获取 B 站详情，复用现有缓存和请求限制；新校验版本重新检查旧标题，不要求清空用户资料。另一设备通过已有来源补全流程得到同样结果。
- 录入播放历史和后台原生切歌保留来源上下文。手动改名由独立标记保护，不能靠标题字符串猜测。
- 来源请求写缓存时持锁校验账号会话，前端应用时还校验观察到的 Track 对象；账号 ABA、新编辑与迟到失败都不能被旧响应覆盖。
- 手机、桌面和大屏使用同一个标题服务与元数据 hook，Android、iOS、鸿蒙后台解析使用共享 Rust 规则。

回归覆盖旧缓存、恢复快照、录入历史、手动改名、统计专有条目、V6 升级、账号 ABA、迟到编辑、默认分 P、真实章节、前缀边界和音乐／非音乐标题。浅深主题与窄屏通过实际页面截图检查。
