# 应用内更新

Android 手机和平板共用一个安装包，大屏版按架构独立检查。macOS 和 Windows 按架构使用 Tauri 签名更新。iOS、鸿蒙和 Linux 检查对应安装包，有更新时打开官网下载。

## 版本与构建

所有平台共用基础版本号。应用以 `0.4.0.1` 显示版本，最后一段是对应平台及架构的构建号。官网下载页显示基础版本号 `0.4.0`。新版本从构建 1 开始，单平台补丁只增加该平台及架构的构建号。客户端先比较 SemVer，同版本再比较构建号。旧清单缺少 `build` 时按构建 0 处理，因此 0.3.7 仍能识别 0.4.0。已有的 0.4.0 测试客户端需要先覆盖安装带构建号检查的正式包。

本机构建通过 `BILIMUSIC_BUILD_NUMBER` 指定构建号，默认 1，正式构建允许 1–50。例如 `BILIMUSIC_BUILD_NUMBER=2 npm run android:local -- build --ci` 只增加 Android 手机和平板的构建号。Android 和鸿蒙的系统安装序号随构建号增加，iOS 和 macOS 使用独立的 Apple 构建号。应用标识与 Android 签名沿用之前的版本。桌面 CI 可选择安装目标与构建号。

发布时，`build-info.json` 为每个安装包记录 `build`。单平台补丁的 `platforms` 仅列出本次生成的包，准备脚本从当前发布清单和 `--previous-updater` 复制其他平台记录，校验构建号递增，并生成新文件名。发布同一版本的回退包时同样使用更高的构建号。

应用打开 10 秒后检查，运行期间每 12 小时复查。失败后最早 15 分钟重试。发现新版本时，「我的」或大屏设置入口出现圆点。点击「下载更新」先查看本机版本至目标版本之间的更新内容，确认后开始下载。需要从官网安装的平台在确认后打开官网。下载完成后由用户确认安装，退出或重启前保存本地播放队列和进度。

## 下载与安装

- 官网不可达或返回备案拦截页时，读取 Gitee、GitHub 的 main 分支清单。安装包也支持双源回退。
- Android 下载后校验清单中的大小和 SHA-256，再由系统确认包名、签名与版本。手机版与大屏版不能相互覆盖。首次安装更新可能需要允许“安装未知应用”，授权返回后再次点安装。
- 桌面端校验 Tauri 更新签名，更新包与普通 DMG／NSIS 安装包分别发布。macOS 使用 `.app.tar.gz`，Windows 使用 NSIS `.exe`。
- 后端生成一次性更新计划，前端只提交计划 ID，不能指定下载安装地址。下载／安装串行，离开设置不会重复开始下载。
- 更新包只保留在应用缓存中，不混入音乐下载目录。Android 新下载会清理旧 APK 缓存。

没有安装能力或签名更新包时保留官网入口。

## 生成发布说明

每项改动在 [`docs/changes/`](changes/) 记录一次。[CHANGELOG.md](../CHANGELOG.md) 提供待发布预览和已发布日志的入口。`prepare_release.py` 默认从各端已经发布的 `sourceCommit` 到本次实际构建的 `source` 生成说明。GitHub 和 Gitee 的说明保留技术条目及 PR 链接，官网补充简短的改动摘要，客户端从发布清单的 `updateNotes` 读取适用于本次更新的记录。未发布的平台继续使用原有记录。相同构建号的安装包替换保留已有应用内更新记录，官网和发布页仍可补充本次改动。

准备本地候选时沿用 `--build-dir`、`--output`、`--revision` 和 `--previous-manifest`，平台补丁仍需 `--previous-updater`。新平台或旧清单缺少来源时，用 `--changelog-base <完整提交号>` 指定缺失平台的基线。本机需要相应的 Git 提交。保留 `--notes` 与 `--patch-change` 用于手动历史发布。

## 桌面签名与构建

仓库仅包含 `src-tauri/update-public-key.txt` 公钥；私钥不能提交。开发机私钥默认读取 `~/.config/BiliMusic/keys/updater.key`，应离线备份，勿在新发布时重新生成。

```sh
npm run build:updater
```

也支持 `TAURI_SIGNING_PRIVATE_KEY`（私钥内容或路径）与 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。GitHub Actions 配置同名 Secrets 后自动产出签名更新包；没有配置时仍可构建普通测试安装包。私钥密码为空时不必配置密码 Secret。分发前确认签名公钥与客户端内置公钥一致。

收集构建产物时，将 macOS `.app.tar.gz` 及同名 `.sig`、Windows原始 `.exe` 及同名 `.sig` 一起放入 `build-info.json` 所在构建目录。现有 `prepare_release.py` 会生成带版本／修订号的 OTA 资产和 `updater.json`；`validate_bundle` 检查大小、哈希、签名文本与公钥 ID。客户端在安装前完成密码学校验。签名或归档缺失不能伪装成支持桌面 OTA。

发布流程先上传并校验安装包、归档、签名，再激活 `updater.json`，同步到官网、Gitee 与 GitHub。不得把本地测试包写入线上清单。普通安装包的 `releases.json` 和现有回滚流程保持不变。

## 官网与统计

网站新增：

- `GET /api/v1/updater`：返回桌面签名清单，没有可安装更新时返回 204。
- `POST /api/v1/update-download`：客户端完成一次下载后，提交版本、平台和 `source=ota`，累加已有主页下载统计。不发送设备或账号标识。检查更新、下载失败、重复点安装都不计数。

计数失败或官网备案拦截不会阻止安装，不循环补报。此统计是下载次数，不代表安装成功或独立用户数。

部署网站时需要更新服务代码与 Docker 镜像。将发布目录整体只读挂载给网站，并用 `UPDATER_MANIFEST_PATH` 指向该目录的 `updater.json`；挂载目录可读取原子替换后的新文件，避免单文件 bind mount 固定在旧 inode。未部署接口时，客户端仍可从双镜像更新，但官网不会计入 OTA 下载。

## 验证边界

自动测试覆盖清单平台隔离、旧清单回退、损坏／截断安装包、过期计划、并发点击、晚到进度、安装权限重试、安装包身份校验和发布资产映射。常规发布核对安装包版本、构建号、签名和更新清单。复用同一安装包的测试结果，安装器、签名或启动流程有变更时验证受影响的平台。

## 交付收尾清单

### 合并或推送

- [ ] 核对实际提交范围和影响平台，保留外部 PR 的作者提交。在同一批代码中补齐 [更新日志条目](changes/)，包括内部维护，运行 `python3 scripts/release_changelog.py --check`。有相关 Issue 时，记下可回溯的修复提交或发布版本。
- [ ] 核对远端目标分支已收到预期提交。同步本地工作区时先保护未提交的修改。

### 构建交付

- [ ] 记录实际构建源码、完整版本、目标平台和架构。用本地工作区构建时注明是否包含未提交改动。核对最终安装包的标识、适用签名及覆盖安装条件，交付可用的安装包路径。线上清单只收录正式发布并验证过的产物。
- [ ] 合并或构建收尾时检查 GitHub 临时分支。先取回所需 CI 产物，确认源码有主分支、发布标签或其他保留引用。按任务授权清理已合入或明确废弃的临时分支。保留长期维护分支和仍有开放 PR、运行中的 CI、发布流程或工作区依赖的分支。

### 正式发布

- [ ] 按各发布目标自上次正式发布以来的源码范围检查更新日志，包含其他工作区或协作者已合入的改动。核对本次目标的版本、构建号、下载链接与更新说明，并保留其他平台的当前条目。
- [ ] 先上传并校验两处镜像的安装包与所需签名，再切换官网和镜像 `main` 的下载清单及适用的 `updater.json`。按 [官网发布说明](../website/README.md#发布安装包) 核对官网、GitHub 和 Gitee 的下载与更新地址，使用客户端实际读取的地址验证。完成后同步本地 `main`，保存发布报告和回退资料。
- [ ] 三处复核通过后再清理失效资产。Gitee 保留最新正式 Release，仅清理当前下载或更新清单已无引用的旧 Release 和附件。保留 GitHub 发布历史、源码标签、最新安装包、签名材料、当前发布缓存和回退所需的文件。
