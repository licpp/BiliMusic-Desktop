# BiliMusic 托管与同步扩展边界

当前只上线官网与反馈服务。本文预留后续扩展约定，不代表客户端已经支持云同步或坚果云。

## 域名和部署职责

| 域名 / 路径 | 用途 | 当前状态 |
| --- | --- | --- |
| `bilimusic.cn` | 官网、下载声明、反馈 | 本次部署 |
| `www.bilimusic.cn` | 跳转到官网 | 本次部署 |
| `/api/v1/policy`、`feedback`、`releases`、`health` | 官网 API，有版本边界 | 本次启用；兼容旧 `/api/*` 路径 |
| `api.bilimusic.cn` | 将来的账号和同步服务，独立容器及数据库角色 | 仅预留名称，尚未添加 DNS 或提供接口 |
| `downloads.bilimusic.cn` | 安装包、校验值与发布清单；可接对象存储/CDN | 仅预留名称，当前无安装包分发 |

官网只处理反馈；未来不把用户歌曲数据塞进 `feedback` 表，也不把账号、同步服务和官网部署绑定。API 采用 `/v1` 版本路径，与当前静态页面可分别发布。只有相应服务准备就绪后再增加子域名解析，避免提前暴露无认证端点；不配置泛域名解析。

官网目前同源调用 `/api/v1/*`，不启用宽泛 CORS。未来客户端账号 API 独立使用短期访问令牌、刷新令牌轮换与设备撤销；Web 管理页另行考虑 Cookie/CSRF，不复用反馈接口的匿名身份。

## 客户端以本地为主，云端由用户选择

建议在 Rust 领域层定义 `SyncProvider`，UI 与 SQLite 仓储只依赖领域接口，不直接写远端 SQL 或调用具体云商 SDK。建议操作：连接检查、读取清单、带版本条件的写入、列举变更、删除及断开连接。首次进入设置默认 `local_only`，用户明确选择后才读取远端或上传。

三个提供商：

- `local_only`：现有 SQLite；不联网同步。
- `bilimusic_cloud`：用户自愿注册并选择上传到项目服务器。账号和数据按用户隔离，数据库使用独立角色/库；表单反馈与同步数据隔离。
- `webdav`：客户端直连用户自己选择的坚果云等 WebDAV 服务。使用应用专用密码，凭据写入 macOS Keychain / Windows Credential Manager；不经由项目服务器，不放进同步数据或日志。

保持提供商注册与协议适配独立。WebDAV 使用标准 HTTPS/WebDAV，并在上线时核实服务商当前接口、配额与条件写入行为。切换提供商前必须明确选择合并、覆盖或保持本地，不因切换自动删除任一方数据。不得把示例 URL 或域名当作隐式上传授权。

## 同步内容与格式

第一阶段只同步用户创建的数据：歌单、收藏、metadata 覆盖、歌词选择与时间偏移、可选择的播放偏好。音视频文件、B 站 Cookie、第三方账号令牌、下载路径、设备信息和浏览历史默认不上传；搜索/播放历史需单独开关并说明用途。

独立分 P 主键继续采用 `bilibili:{bvid}:{cid}`，改歌曲名不改变身份；歌单用 UUID。通用同步清单至少包含 `schema_version`、用户/设备命名空间、记录 ID、记录类型、`revision`、`updated_at`、删除墓碑、可选内容摘要。版本不支持时拒绝覆盖并提供导出/升级路径。

建议先做小规模 JSON 快照 + 按记录版本合并，避免第一阶段就引入整库复制。WebDAV 将应用数据存于独立目录，以 ETag/If-Match 做条件更新，临时文件上传后再提交清单；提供商不支持条件写入时应提示冲突并保留双方副本，不能默默覆盖。自有服务器用事务及乐观锁，返回 409 冲突和远端版本。时间戳只用于展示，不依赖设备时钟决定唯一胜者。

## 上线同步前必须补齐

- 用户身份、逐用户授权和数据库行隔离，服务端不要信任客户端传来的 user_id。
- 上传前明确展示数据范围、提供商、存储位置和保留策略；提供立即同步、暂停、解绑、导出和删除云端数据。
- 密钥安全存储、传输 HTTPS、请求与存储配额、重试退避、增量迁移、删除传播与恢复方案。
- 可选客户端加密需另行设计密钥恢复及丢失风险，不把服务端存储默认描述为端到端加密。
- 更新隐私说明和同意版本；现有反馈表单的同意只覆盖反馈处理，不能作为歌曲数据上传的授权。
- 为域名公开服务核实备案状态；同步和个人信息处理上线前重新核查适用要求。

这些工作不属于当前已上线能力，不在官网宣传为已支持功能。
